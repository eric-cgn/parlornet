# Identity, sign-in, sessions and the extension channel (security design)

This is the design the code follows. docs/accounts.md describes sign-in for operators and players, docs/protocol.md the wire.

## Assets

1. A player's ability to act as themselves: move, resign, invite, chat, change their password. Taking it over is the main thing to prevent.
2. Credentials: passwords (sign-in password), temporary passwords (mailed at sign-up email and for a forgotten password, or given by the operator's reset), the admin password.
3. Sessions: proof that a sign-in happened, held by a server extension for a player.
4. Sign-in keys: what a computer where the player chose Stay signed in keeps instead of the password (Staying signed in, below).
5. Extension keys: proof that a program is one of this parlor's server extensions (and, with the admin role, its admin adapter).
6. Availability of sign-in for honest players.

## Attackers

| Who | Can | Must not be able to |
|---|---|---|
| Anyone on the internet, at the public ports (6500-6508, 6512-6521 and 1744) | open connections, send anything, guess | sign in without the credential; resume a session; reach the extension channel or the admin socket |
| A curious or malicious player | everything a player can; read their own pages, URLs, cookies | act as another player |
| Someone who sees a URL, a log, a screenshot or browser history | read whatever was there | find a credential in it; find a working session id in it (cookie browsers; see Accepted risks for browsers without cookies) |
| A compromised server extension (its key stolen, or code execution in its process) | speak the protocol on the extension channel as that server extension; with code execution in the default single-user container, read what that user reads (see Containment) | resume sessions issued to other server extensions; sign in as a player without that player's credential (except under `none`); make admin requests; with a stolen key alone, or with code execution under either opt-in containment, read the database or another extension's key |
| An impersonated core or server extension (no key) | answer or open connections on the server extension port | complete a TLS handshake |
| Someone holding a copy of the database | read it offline | use passwords, temporary passwords, session ids or sign-in keys from it (they are hashed); see Data at rest |
| Someone who copies a disk or a browser profile that holds a sign-in key | sign in as that player where the key was given, until it is forgotten or expires (Staying signed in) | learn or change the password, get more keys, use the key through another listener or server extension, or keep using it after the player signs out there, changes the password or forgets that computer |
| An operator mistake: publishing the server extension port (6590) or the admin socket (6599) | - | turn that into player takeover or admin access: both need a key |

In code the extension channel is `--frontend-port`, `parlord/frontends.py`, `--key` and the key role `frontend`, names from before the project settled on "server extension" (docs/architecture.md); in this document a frontend is the program a player uses.

## Trust boundaries

```
 8-bit / native clients --plain text, 6501----------------------------> core: public listener
 browsers --HTTP 6500--> web            \
 terminals --telnet 6502--> telnet      |
 Eclipse --IOS 6503--> ios              |
 FIBS clients --6505--> fibs            |
 Outland Gateway --6506--> outland      |
 BobGrid, MUD clients --6507--> doom    |
 GameMaster --6508--> gamemaster        > TLS 1.3, PSK per extension, 6590 --> core: extension listener
 NetBoxes --6512--> netsprocket         |
 browsers via TLS proxy --6513--> play  |
 batnav clients --6514--> batnav        |
 Awale --IRC 6515--> awale              |
 NetLuff --1744 or 6517--> netluff       |
 Networdz --6516--> networdz             |
 xcheckers --telnet 6518--> icds        |
 Worthy Opponent --modem, 6519--> worthy |
 RSCARDS --modem 6520--> rscards        |
 (no port) bot -------------------------/
 operator --telnet 6510--> admin adapter --TLS 1.3, admin-role PSK, 6599--> core: admin socket
                                                   |
                       accounts component (parlord/accounts.py): players, sessions, lockouts
                       sign-in methods (parlord/auth.py): none, password
                       sign-up methods (parlord/auth.py): none, password, email
```

- **Public listener (6501)**: plain text for 8-bit machines. Signs in with the method's credential only; the sign-in lasts as long as the connection and has no id. Never accepts `SES`, never reveals a session id.
- **Extension listener (6590, 127.0.0.1 in the container, or published on a private link for server extensions on another host)**: TLS 1.3 only, a pre-shared key per server extension, role `frontend`. The only place session ids are issued and `SES` and `SRC` (the client's address, for per-address limits) are accepted. Each server extension has its own share of its connections (see Lockouts and rate limits).
- **Admin socket (6599, 127.0.0.1)**: the same TLS 1.3 handshake, but only keys with role `admin`; then the admin password. Extension keys are refused at the handshake.
- **Accounts component**: the only code that checks credentials (through the method), creates, resumes, touches, ends and expires sessions, and decides on every request whether a connection is still signed in.

## The auth abstraction

`parlord/accounts.py`, class `Accounts`. The core calls nothing else for identity; server extensions call nothing but the protocol.

| Call | Does |
|---|---|
| `greeting()` | `AUTH=signin SIGNUP=signup LABEL=...` |
| `begin(conn, name, given, mode)` | `HELO` (mode `any`), `USER` (`signin`: an unknown name is refused), `REG` (`signup`: a taken or reserved name is refused); `given` is the second word, handed to the method |
| `answer(conn, field, value)` | `AUT` |
| `resume(conn, sid)` | `SES`: server extension connections only, sessions issued to that server extension only |
| `current(conn)` | on every request: the signed-in player, or None; signs out a connection whose session was ended or grew past its absolute age; touches the session |
| `sign_out(conn, everywhere)` | `OUT`, `OUT all`; forgets the session's sign-in key, or with `all` every key |
| `key_issue`, `key_list`, `key_forget` | `KEY NEW`, `KEY LST`, `KEY DEL` (Staying signed in); the key itself is checked by the sign-in method (`AUT key`) through `key_check` |
| `change(conn)` | `PWD` (sign-in password only): the change steps; ends the player's other sessions |
| `suspend`, `reset`, `delete` | for the admin: each ends every session of the player |
| `sweep()` | drops expired sessions, deletes pending accounts past their 24 hours |

Behind it, `parlord/auth.py` has two registries, run as one dialog (class `Auth`): **sign-in methods** (`none`, `password`), which check a credential at every sign-in and own recovery, and **sign-up methods** (`none`, `password`, `email`), which make the account and set up what the sign-in method needs. Pairs that work: `none`+`none`, `password`+`password`, `password`+`email`; others are refused (`combo_problem`). Each step is generic: `info` lines, `ask` (text, secret or yes/no, maybe flagged `cred` or `new`), then `ok player` or `err code text`. A method never issues anything that outlives the flow except the credential it sets up (a password hash, or a temporary password's hash with its time). Temporary passwords go by mail, never through a server extension; verification is always the mailed password typed back, never a link. After `ok`, `Accounts` refuses suspended players and creates the session; this holds for `none` too.

| Sign-in | Credential | `HELO name x` | Recovery |
|---|---|---|---|
| none | the name | ignored | - |
| password | a password the player chose (8 to 64 printable ASCII, at least three of lowercase, capitals, digits and symbols), or a temporary password (24 hours), after which a new password must be chosen before the sign-in completes | refused: the password is asked for | address on file: `reset` at the question (also while locked) mails a temporary password, and the old password works until it is used; else the operator's reset gives a temporary password and ends the old one |

**Sign-up email and pending accounts.** Sign-up `email` makes a pending account at the address step and mails it a temporary password (`auth.temp_password`: three groups of four from 31 characters, about 59 bits; only its scrypt hash and expiry are stored). The first right sign-in with it confirms the account and asks for a password of the player's own before any session exists; a frontend that cannot ask gets `ERR NEWPASS` and no session. A pending account that nobody signs into within 24 hours is deleted by the core's sweep. A pending account has no recovery: `reset` there is checked as a wrong password, so the answer is the same whether or not its mail went.

There is one other way in: a sign-in key, for a computer where the player chose Stay signed in, accepted only as the answer to the password question of a sign-in (Staying signed in, below, has the decision record). There is no other token and no resume credential. A session id is never accepted where a credential is.

**Sign in and sign up apart (`USER`, `REG`).** `USER` signs in only and `REG` signs up only, so a mistyped name at a sign-in never becomes an account; `HELO` still does either, for older clients. What they disclose is what `HELO` always did: whether a name has an account (`HELO` for a free name starts a sign-up). Names are not secret here (the lobby, `LST`, `who` and invitations show them; `INV` to an unknown name is `ERR NOPLAYER`), so the design does not hide them; it limits how fast they can be listed: `USER` for a name with no account counts against the client address in a budget the size of the sign-up one (20 in 10 minutes, `ERR BUSY wait=N` after), so it lists names no faster than `HELO` could. Email addresses stay undisclosed exactly as before (finding 5): `REG` reaches the same email dialog. The web's and telnet's messages for an unknown name ("There is no account named x here") and a taken one ("The name x is taken") say what the core's codes say and nothing more; they never say whether a name has an address or is locked. The words `new` and `guest` are reserved in the core (`auth.RESERVED_NAMES`, checked when any sign-up starts and again when the account is made), so no account can stand behind a frontend's keyword; so are names that would pass for the server or its staff in a chat (`parlornet`, the server's own name, `admin`, `sysop` and the like). New names also have at least one letter and have `-` and `_` only between letters or digits (`auth.NEW_NAME_RE`, the same two checks, `ERR NAMERULE`).

**Never volunteered.** Server extensions sign in with the name alone. A password their client already supplied answers only an `ASK` flagged `cred` (the first one, or every one for a client that cannot be prompted), and is dropped if none comes: under `none`, and for every step of an email sign-up except choosing the password. Tests assert this on the lines the core receives (`tests/test_ios.py`, `tests/test_fibs.py`).

**Step kinds and `CAN`.** A server extension declares the kinds it can show (`text`, `secret`, `yn`, `info`). A step outside them is refused with `ERR CANNOT`; the method's state for that sign-in is dropped. Notes (optional info) are sent but not required.

## Sessions

- Extension channel: an id of 128 random bits (`secrets.token_urlsafe(16)`, 22 characters), returned once in `OK sid`; only its SHA-256 is stored. Public port: no id; in memory; ends with the connection.
- Bound to the server extension that created it (its key name), to the fingerprint of the key it held then, and to the method in force; `SES` from another server extension, with another key (rotated), or after the method changes, fails.
- Expiry: idle `session.idle_secs` (default 7200) checked when resuming; absolute `session.max_secs` (default 86400) checked on every request, live connections included.
- Ended by `OUT`, `OUT all` (live connections too), a password change (all others), a recovery (all others), the admin's suspend, reset and delete, a change of either method, the rotation or removal of the issuing server extension's key (the sweep), expiry. A live connection whose session ended gets `ERR SIGNEDOUT` once.
- Stored in SQLite (`sessions`: hash, player, server extension, key fingerprint, method, created, used, and `devkey`, the number of the sign-in key it signed in with or was given), so server extensions keep working across a core restart; `used` is written at most once a minute.

## Staying signed in (decision record)

**Before.** The design had no "remember me". Every sign-in took the password, a session lived only in a server extension and for at most 24 hours, and an 8-bit player typed the password at every connection.

**Decided (2026-11-26, approved by the project's owner).** A computer may stay signed in with a key of its own, as a setting of the client, Stay signed in, that every client may offer through the same requests. A password typed on an Apple IIe or a C64 at every connection, on keyboards that make that slow and error-prone, is a real cost, and browsers drop the web's session cookie when they close. A key per computer saves that without keeping the password anywhere.

What was decided, and why:

- **A setting, not a question.** The client's Stay signed in setting (the 8-bit settings screen, a checkbox on the web's and Play's sign-in forms) decides it. With it on, the first successful sign-in with the password gets the key, with nothing more asked. A client that cannot keep data of its own, such as a telnet program, does not offer it. No client has rules of its own.
- **Issued only right after the password.** `KEY NEW` works once, on the connection that has just signed in with the password (or chosen a new one), never on a session resumed with `SES` and never after a sign-in with a key. So a stolen session id, a compromised extension's sessions or a key itself cannot be turned into another key.
- **The key.** A key is 128 random bits (`secrets.token_urlsafe(16)`), like a session id. Only its SHA-256 is stored, because a slow hash adds nothing at 128 bits. The server keeps it with the player, the channel it was given on (the server extension's key name, or the public port), a label, and when it was made and last used. It is on the `OK` line once and nowhere else.
- **It answers the password question (`AUT key`)** rather than being a sign-in request of its own, so it goes through the same code as the password: the per-name lock (one check at a time), the password-check rate, the lockout and the budgets, the suspension check, the trusted address and the session's creation in `Accounts.finish`. There is no second sign-in path to secure, and the client's fallback is the same dialog: on `ERR NOKEY` it asks for the password. The requests that are not sign-in steps (issue, list, forget) are one verb with subcommands, `KEY`, as `PRF` and `PFL` are.
- **Bound to its channel.** A key works only where it was given: a key from the public port does not sign in through the web, and the web's does not sign in on the public port or through Play. A compromised extension can use only the keys of its own clients, which pass through it as their passwords already do.
- **Compared in constant time.** `Accounts.key_check` hashes the answer and compares it with every live key of the player with `hmac.compare_digest`, with no early end, and the channel the same way (tests/test_stay_signed_in.py checks this by reading the code).
- **Wrong keys count.** A refused key is a wrong answer toward the name's lockout and the per-address and server budgets, exactly as a wrong password. A right key signs in while the name is locked or the budgets are spent, as a temporary password does, so someone who locks a name cannot keep its owner's remembered computer out. A wrong key while the name is locked is refused with the wait and not counted again. While a locked name has keys, `USER` still asks the question, which tells only that the locked name has a key somewhere.
- **Forgotten** when the player signs out there (`OUT`, whatever the setting), on `OUT all` (every key), at a password change, a new password after a temporary one and the operator's reset (every key), when the player forgets it from the list (`KEY DEL n`, `KEY DEL all`; the sessions that signed in with it, or were given it, end), after `keys.idle_secs` unused (90 days), and when the account is deleted. At most 20 keys a player.
- **Never seen.** Keys never go in a URL, a page or a log. The web keeps its key in `pnkey` (HttpOnly, SameSite=Lax, Secure over https, `Path=/`), and Play in `pnplaykey` (HttpOnly, SameSite=Strict, Secure with an https public URL, `Path=/play/`). Play's page never receives the key, only a one-time handle for the cookie, and the Play extension signs in with the cookie itself.

**Threats and what limits them.**

| Threat | What the holder can do | What limits it |
|---|---|---|
| A copied floppy, or a disk image shared with a key on it | sign in as the player on the public port, from any machine, without the password | the key is not the password, so it opens nothing else and cannot change the password (`PWD` asks for the current one) or get another key; signing out on the computer forgets it, so a disk copied after that holds nothing; the profile lists every computer with the day it was last used, and Forget ends it at once; a password change forgets them all; 90 days unused and it expires. A disk image made to share should be made signed out |
| A copied browser profile, or the cookie taken from a browser | sign in as the player through the web (or Play) only | the cookie is HttpOnly, so a script on the page cannot read it, SameSite, and Secure over https; the same limits as a floppy |
| A key seen on the wire (the public port and plain HTTP have no TLS) | the same as a stolen key | the same as the password seen on the wire, which is already out of scope (Out of scope); a seen key is less than a seen password |
| Guessing a key | nothing in practice | 128 bits; every wrong key counts toward the lockout and the budgets; checks are at most 30 a minute from one address |
| A copy of the database | nothing | only SHA-256 of 128-bit keys |
| A stolen session id or a compromised extension's sessions | nothing more than the session | `KEY NEW` only right after the password on that connection |
| A thief with a key forgets the player's other computers (`KEY DEL all`) | sign the player out elsewhere | an annoyance, not a takeover; the password still signs in, and a password change ends the thief's key |

The residual risk is a key copied while the player stays signed in and not noticed in the list. It works until it is forgotten, the password changes or it goes 90 days unused (Residuals).

## Extension channel

- TLS 1.3 from the Python standard library with external pre-shared keys (Python 3.13+, `ssl` PSK callbacks): one 256-bit key per server extension, PSK identity = the server extension's name. The core loads no certificate, so a handshake without a known PSK cannot complete. Server extensions verify certificates against an empty trust store, so an impostor core that offers a certificate instead of the PSK fails; both sides also check that the PSK was used (`session_reused`) and the version is TLS 1.3. Key exchange is OpenSSL's default `psk_dhe_ke` (forward secret).
- The core makes a fresh `SSLContext` per connection (plain accept, then `start_tls`) so the PSK callback can record which identity was used; the connection is labeled with that name and the key's fingerprint.
- PSK rather than mutual TLS with a private CA needs nothing outside the standard library (no openssl CLI or `cryptography` in the image) and no certificates to expire or renew; enrollment is one file, revocation is deleting it, and both sides authenticate in the same handshake. Keys are symmetric, though, so the core's key directory can impersonate any server extension; it lives beside the database with the same protection.
- Keys: `<keys>/<name>.key`, mode 600, one line `parlornet-frontend-key 1 <name> <role> <base64url key>`. `python -m parlord.frontends --keys DIR add NAME [--role admin]` enrolls (prints the path, never the key; never overwrites), `rotate NAME` replaces, `remove NAME` revokes, `list` lists (NAME is checked: never a path). The core rereads the directory on each handshake; every sweep (10 seconds) it closes connections whose key was rotated or removed and ends the sessions issued under the old key. The container's start script enrolls each adapter it starts (the admin adapter with the admin role). Where a group `pn-<name>` exists (the container), a key file is owner read-write and readable by that group only (mode 640): each server extension's own user can read its own key and no other.
- Server extensions on another host (deploy/README.md). The channel is TLS 1.3 with a pre-shared key whether the extension runs in the core's container or on another host, and the core treats the two alike. It uses a connection's own address only to share out the handshake slots. A player's address comes from `SRC`, and the ports come from what each extension declares. `deploy/install.sh` enrolls the keys with `PARLOR_REMOTE_EXTENSIONS` and leaves a copy of each for the operator to take to the other host over SSH. With `PARLOR_FRONTEND_PUBLISH` it publishes 6590 on one host address, and `deploy/install-extensions.sh` runs the extensions there against it. Across hosts the channel should run over a private link, such as WireGuard or a private network, with 6590 published on the link's address only. The keys keep out anyone without one, and the link keeps the listener itself off the internet.

## What each server extension may and must do

- May: everything a client may, plus `SES` for sessions it was issued.
- Must open its core connection for a client only once that client has sent a login line, and count and cap its clients that have not signed in (per server extension and per client address, with a short time to log in: `common.Gate`); pass the client's address with `SRC`; never put a control character in a request (`CoreClient.req` refuses CR, LF and the rest for every adapter);
- Must sign in with the name alone; relay the server's steps and the player's answers and nothing method-specific; answer a `cred` question with a password its client supplied and nothing else with it; never log, store or display the answers; hold the session id only where it must resume (the web, Play) and never show it; send `OUT` when the player leaves if it holds one connection per player (telnet, IOS, FIBS, Outland, DOoM, GameMaster, NetSprocket, batnav, Awale, NetLuff); declare its step kinds with `CAN` if it cannot show all of them.
- Web specifics: Sign in (`/login.htm`, `USER`) and New account (`/signup.htm`, `REG`) are separate POST forms; the sign-in form's password field answers the credential question only, and the new-account form has none; the sign-in form's Stay signed in checkbox asks for a sign-in key right after the password, kept in `pnkey=name.key; Path=/; Max-Age=34560000; HttpOnly; SameSite=Lax` (plus `Secure` over https), with which a visit with no session signs in, and which sign-out and a refused key clear; the session id in a cookie `pn=<sid>; Path=/; HttpOnly; SameSite=Lax`, no expiry; for a browser that returns no cookie, `s=<sid>` in links, decided on the first page after sign-in through a one-time 60-second handle (not the id). Every page resumes with `SES`. Actions carry `x=`, an HMAC-SHA256 of the session id under a key derived from the web's extension key, checked in constant time. Credentials go in POST forms only; GET sign-in is ignored. Pages are sent `Cache-Control: no-store`.
- Play specifics (ParlorNet Play, `adapters/playserver.py`): PARLORNET/1 over a WebSocket whose handshake must carry this site's `Origin` (docs/protocol.md, WebSocket); the session id never reaches the page, which trades a one-time 60-second handle for its own cookie, `pnplay=<sid>; Path=/play/; HttpOnly; SameSite=Strict`, plus `Secure` when `play.public_url` is https. With Stay signed in, the key from `KEY NEW` goes the same way, by a one-time handle, into `pnplaykey` (`Path=/play/`, HttpOnly, SameSite=Strict, Secure as above), and the extension signs in with it itself when `SES` alone finds no session. It is a different cookie from the web's `pn`, so a session from one site is never resumed by the other, and the secure one is never sent to the plain-HTTP pages on the same name. A `POST /play/session` with another site's `Origin` is refused. The files go with a Content-Security-Policy that allows only the site's own files and its WebSocket.
- The admin adapter is not a player server extension: admin-role key, the admin socket, then the admin password.

## Behind a TLS proxy

The Play extension speaks plain HTTP on 6513 and is meant to be reached through a reverse proxy on the host that terminates TLS (deploy/README.md); `deploy/install.sh` publishes 6513 on the host's loopback address only (unless `PARLOR_PLAY_OPEN=1`), so only that proxy reaches it.

- **The client's address.** Through a proxy every connection comes from the proxy. The setting `play.proxies` lists the proxies' addresses or networks; for a connection from one of them, the extension takes the last address in `X-Forwarded-For` that is not itself a listed proxy, and the scheme in `X-Forwarded-Proto`. That address goes to the core as `SRC` and keys the extension's own per-address limits. From any other address both headers are ignored, so a client that reaches 6513 directly cannot choose its own address. Without the setting, every player behind the proxy shares the proxy's address and its limits; that is safe but crowded. Listing an address that is not a proxy lets whoever connects from it pick any address for the per-address limits; it gives no session and no sign-in.
- **The origin.** With `play.public_url`, the WebSocket accepts only that URL's origin, so a page of another site cannot open one with the player's cookie, whatever `Host` the proxy passes. The cookie is `Secure` when the URL is https.
- **No HSTS.** The extension never sends `Strict-Transport-Security`. A browser applies it to every port of the name, so it would force https onto the 1997 pages on port 6500, which have no TLS, and turn modern browsers away from them. The proxy should not add it either.
- **The certificate** is the proxy's business (Let's Encrypt with certbot, for example); the container holds no certificate and no private key.

## Dial-in gateways (PROXY)

A dial-in gateway carries modem calls to the dial-in extension on 6521, and may open each connection with a PROXY protocol header, version 2 (docs/protocol.md, Dial-in gateways). The header says that the connection is a call, may name a source address, and says how long the call has been up. The core believes it only from the addresses and networks in the setting `dialin.gateways` (`PARLOR_DIALIN_GATEWAYS`), which it matches the way the web matches `web.proxies`. The setting is empty by default, and then the core believes no header at all. A gateway that connects to 6501 itself is read by the same rules.

- The dial-in extension decides nothing about trust. It reads the header with the core's code, and it asks the core with `DIA addr` whether the address its connection came from is listed. It passes a call to the native protocol to the core with the header as it came (`DIA NATIVE addr`), and the core reads the header again with the same check. The core takes `DIA` only from the extension whose key is named `dialin`, so no other server extension can say that a connection is a call or choose the address it comes from. The core trusts no address for being on its own network, loopback included.

- A header from any other address is a protocol error. As soon as the 12-byte signature has come, the core sends `ERR PROTOCOL wrong protocol` and closes the connection, before any opening or greeting. A forged header gets no class, no address and no time limit, and the connection gets nothing else either.
- A listed gateway's header that is cut short, longer than 512 bytes after its first 16, or not well formed is refused the same way. The header counts toward the opening's 20 seconds, so a gateway that sends half a header holds its connection no longer than any other client.
- A listed gateway can choose the source address that the per-address limits count, as a listed web proxy can with `X-Forwarded-For`. It cannot sign anyone in or resume a session. Listing an address that is not a gateway lets whoever connects from it do the same, and puts their connections under the dial-in limits.
- The caller ID, the number dialed, the modulation and the rate stay with the connection in memory. The core never stores or logs them.
- The dial-in limits (docs/protocol.md, Time allowance) charge minutes to the player signed in on a call and to the parlor's pool. Anyone who can call a gateway can use up the pool with calls that never sign in, and then every new call is closed until the month ends. That is the cost of a shared pool, and the operator can set `dialin.pool_month_mins` to 0 to have none.

## Data kept per extension and player

`PRF` (docs/protocol.md) lets each server extension keep a little data with a player, such as a display setting.

- **What**: keys of up to 12 of `[a-z0-9_-]` and values of up to 56 printable ASCII characters (checked by the core; nothing else is stored), at most 16 keys and 1024 bytes per namespace and player (`Limits.pref_*`). Table `prefs` (namespace, player, key, value), in the clear.
- **Isolation**: the namespace is the server extension's key name from its TLS handshake, never from the request; the player is the one signed in on the connection. There is no request that names another player or namespace, so a compromised extension reaches only its own data, and only for players it can act for already (sessions it was issued). The public port has one namespace of its own, `:native` (no key name has a colon), for the player signed in there with their credential.
- **Never secrets**: extensions must not keep credentials, session ids or anything private there. The operator's admin menus show per player how many keys and bytes each extension keeps, never the values; under sign-in `none` anyone can sign in as anyone and read that player's data.
- **Deletion**: deleting an account deletes its data in every namespace, so nothing passes to whoever takes the name next. A removed extension's data stays until the account is deleted.

## The bot

The bot (docs/bot.md, `bot/`) is a player program, run as a server extension of its own with no port: it serves no clients, so it has no gate, no `SRC` and no credentials to relay.

- **Its key and its names.** It holds one extension key, named `bot` (role `frontend`), enrolled, rotated and revoked like every other (`python -m parlord.frontends`); rotation or removal closes its connections and ends its sessions at the next sweep, as for any extension. A connection with that key may sign in, with the name alone and no question asked, as `bot`, `bot1`, `bot2` or `bot3`, and as nothing else (`ERR RESERVED`). Every other connection, on any listener and under every sign-in method, `none` included, is refused those names on `USER`, `HELO` and `REG` (`ERR RESERVED`). So nobody can sign in as a bot, and the bot cannot sign in as a person. The check is in the accounts component before the sign-in method runs (`parlord/bots.py`, called from `Accounts.begin`).
- **No credential.** A bot account has no password or address; the key is the only secret the bot holds. Its sessions are ordinary extension sessions (hashed, bound to the key's fingerprint); it resumes them with `SES` on its own connections only.
- **The accounts.** A bot account is made at the bot's first sign-in and flagged in the database (`meta` key `bot:<name>`), and the flag is shown in `LST` (`bot=`) and `VUE` (`BOT`), so players can tell a bot from a person. Players cannot delete any account; the operator can suspend or delete a bot account like any other (a suspended bot cannot sign in; a deleted one is made again at the next sign-in). An account that held a bot name before the names were reserved stays its owner's and is never a bot.
- **What a stolen bot key gives.** Its holder can act as the bots: sit down at tables a bot was invited to, and move, chat and resign there. It cannot act as any person, make accounts or resume another extension's sessions. Under the default one-user container the key is as exposed as the others (Containment); under the opt-in user per process the bot runs as `pn-bot` and reads only its own key.
- **Behavior.** It joins only when invited, never invites, keeps under the core's per-connection rate limit with its own pacing, waits with `WAT`, caps its tables per name (20), and opens at most three TLS handshakes at once so it never holds the core's handshake slots.

## Lockouts and rate limits

- **Wrong answers, per name**: every wrong answer counts (a password, a temporary password or a sign-in key): the first two are only refused (`ERR WRONG`), then 1 minute after the third, 15 after the fifth, growing to at most 4 hours; each 8 hours without a wrong answer halve the count; survives restarts. While locked, the account's password is not checked, but recovery by mail still goes ahead (its own limits, below) and a temporary password is still checked, so the owner can get in with a mailed one; a wrong answer while locked is refused with the lock and not counted again. Sign-ins for the same name are serialized (one check and save at a time).
- **Trusted addresses**: a client address from which a name signed in successfully (any method) is trusted for that name for 30 days (table `trusted`, forgotten when the account is deleted). The client address is the public port's peer, or what a server extension passes with `SRC`. IPv6 counts by its /48 everywhere (trust, budgets, caps, eviction choices): one subscriber or site can hold a whole /48, 65,536 /64s, so a /64 key would let one attacker look like many; the cost is that a site's users behind one /48 share its limits, as IPv4 users behind one NAT do.
- **Wrong answers, per client address and for the server**: a wrong answer for a name its address is not trusted for also counts against that address (12 a day; then `ERR LOCKED wait=N Too many wrong answers from your address`) and against the whole server (48 a day; then `ERR BUSY wait=N Too many wrong answers on this server; try later, or answer reset`). These are checked before a credential is: once spent, nothing more is checked for untrusted addresses. A trusted address is never held up by them (only by the name's own lockout), and recovery by mail is never held up by them. Kept in memory; the admin menus' Status screen shows them (with an alarm when one is used up) and can clear them without a restart (the per-name lockouts survive both).
- **What that allows**: across many names, from any number of addresses, untrusted guesses at passwords are at most 48 a day for the whole server, which is under one guess per name per day once a server has more than 48 players, and the number does not grow with the number of players or addresses. One address alone gets 12 a day. At one name, the name's lockout allows about 6 a day. So an online guesser gets in only with a password that is among the first few hundred guesses for that name over months; the password rule (8 characters or more, three of the four kinds) keeps the commonest choices out, and nothing more is claimed for chosen passwords. In exchange, during a sustained attack from a handful of addresses, a player signing in from an address they have not signed in from before is refused until the day's budget frees or the operator clears it (Residuals). A temporary password has about 59 bits (31^12, about 7.9e17 values) and works for 24 hours. Guesses at it count like any wrong answer while the name is not locked; while the name is locked they are refused unchecked unless right, bounded only by the password-check rate (30 a minute per client address). Even at that rate from 1,000 addresses, about 4.3e7 guesses in its day, the chance of finding it is about 5e-11. tests/test_review_fixes.py and tests/test_retest_fixes.py check the budgets against the defaults.
- **Recovery mail, per requester**: one client address may ask for a name's recovery mail twice a day. Besides that, a name's recovery mail from untrusted addresses shares 4 a day (no hourly cap per name), and an address's 3 an hour and 6 a day. Recovery asked from an address trusted for the name (its owner's) is logged as the owner's own and is held up by none of those shared caps, only by its own two a day and the owners' server budget. **Two server budgets**: owners' own recovery (asked from a trusted address, or finished by signing in with the mailed password, which moves it from the strangers' count to the owners') has 20 an hour and 60 a day; everything else, strangers' requests, has its own 3 a minute, 20 an hour, 60 a day. Strangers' resets can use up only theirs. Both show in the admin Status screen and are cleared with the wrong-answer budgets (Clear budgets). The trade-off is that one stranger address can use 2 of a name's 4 a day, so it takes two addresses to use up the day for an owner on a new address; the owner on an address they have signed in from is not affected. Counting only requests that end in a sign-in would have let strangers mail an address without bound, so the per-name and per-address caps stay for untrusted requests.
- **Password checks**: at most 30 a minute from one client address (scrypt work, also for correct passwords); at most 2 scrypt hashes run at once.
- Wrong `SES`: nothing is locked. Three failures on one connection, then `ERR RATE` there; failures per server extension are counted in the log. The web stops resuming for a client address after 10 failures in 10 minutes, except for a session id that has resumed there before or was just issued there (so a neighbor behind the same address cannot sign everyone out, nor keep a newcomer out); it no longer clears the cookie when it stops.
- **Connections**: separate caps for the public port (120; a connection that has not sent `PARLORNET/1` within 20 seconds is closed, so idle connects hold a place only that long, and one that has not signed in within 5 minutes of connecting or of signing out is closed too), the extension channel (1200 in all, at most 250 per server extension) and the admin socket (8 signed in). Unauthenticated sockets on the extension channel and the admin socket get 3 seconds to finish the TLS handshake, at most 8 (admin socket: 2) from one address and 64 (admin socket: 8) in all; a new one over either limit ends the oldest handshake of its own address, or of the address with the most, so idle sockets cannot hold the slots. Every shipped server extension stays well under its share: it opens a core connection only for a client that has sent a login line, and keeps clients that have not signed in to max(20, its signed-in cap), 4 from one address (IPv6: one /48), 2 minutes per login line, 10 minutes to finish signing in. A newcomer over its address's limit ends that address's least recently active pending connection. When all places are taken, the newest arrival at an address holding more than the newcomer's would is closed; if no address does (every one holds one, say), the newcomer, the newest arrival, waits outside: many addresses with one connection each cannot close a player already signing in. The web: 80 requests (a kept-alive connection counts as one while it is open: it carries at most 16 requests, waits at most 5 seconds for the next, and is offered only while the web and the client's address are at most half way to these caps), 20 from one address, and 100 sign-in dialogs, 4 from one address (IPv6 /48), 5 minutes each; when full, the same rule (the newest dialog of an address holding more than the newcomer's would, else the newcomer gets Busy). Per-connection request rate limit as before.
- Sign-up: at most 20 sign-ups started from one client address in 10 minutes. A chosen password is hashed once, after its confirmation matched (a mismatch costs nothing). A temporary password is hashed once, when it is made.
- **Sign-up email, per address** (`signup.address_cooldown`, 7 days): an address gets at most one sign-up email (the temporary password, or the notice to an address that already has a name), then none for the cooldown. A sign-up naming it again in that time is answered as if its mail went (below) and nothing is sent. The cooldown is kept by a keyed hash of the address (Data at rest), started when a mail goes, never lengthened by repeats, and lifted only by its end or by the operator (one address, or all). So through sign-up the server sends one person at most one mail a week, 52 a year, whoever asks and from however many addresses; before, the per-address caps allowed 6 a day, 42 a week, notices to an account's owner included.
- **Pending accounts** (`signup.max_pending`, 60): a pending account takes a place when its address step is done and holds it, and its name, until someone signs into it or its 24 hours end; then the sweep deletes it and its place and name are free, but not its address's cooldown. While every place is taken, sign-ups are refused before anything is asked (`ERR BUSY wait=N Too many sign-ups in progress`). Every pending account passes the mail caps and counts as a sign-up mail (also when the cooldown holds its mail back), and the server-wide cap is 60 sign-up mails a day, so at the defaults the places fill no faster than a day's mail allows. Someone who fills them all keeps others from signing up by email for up to a day (Residuals); whatever their number, they cause at most one mail per distinct address a week, within the daily caps (60, 30 to new addresses).
- **Indistinguishable answers** (finding 5 kept): at the address step every case answers with the same lines, passes the same caps, counted the same way, does the same hashing and makes a pending account of the same shape: a mail that goes (the temporary password), the notice to an owner, and a mail held back by the cooldown. Held mail also takes about as long as sending has lately (a moving average of the relay's send times, at most 15 seconds). The lines after the address are the same for all: "If you haven't received the email, it may take a while; you can ask again after 7 days." In the notice and held cases the account's temporary password hash is of a password nobody was sent, so nothing signs in to it, and `reset` answers the same for every pending account. Only a mail that went carries a password that works.
- Email: the caps in docs/accounts.md, with separate budgets for sign-up and recovery, per-client-address caps, and the recovery rules above; they stay as defense in depth under the sign-up rules. Recovery mail to an address on file is outside the sign-up rules: its own caps, as before.
- The admin password: per client address of the operator (passed by the admin adapter), the players' schedule, in memory.

## Paged replies

A public-port connection that asked for pages (`PAG`, docs/protocol.md, Paged replies) keeps the rest of a long reply in memory until the client sends `CNT`. That is the only state paging adds, besides one number for the page size.

- **The bound.** The rest is part of one reply the server has already made, and nothing is added to it while it waits. The next request other than `CNT` drops it, and so does the close, whether the client closes or the server does for `ERR IDLE` or `ERR LIMIT`. So a connection holds at most one reply. Without paging the same reply goes into the connection's send buffer at once, where it stays until the client reads it, so a client that reads nothing holds as much either way.
- **The longest reply.** On the public port that is `LST clients` for a player who is seated at, invited to or the creator of every table, because a player's own tables are all listed. It has one `TAB` line and up to eight `CLIENT` lines for each of `games.tables_max` tables, and each line is at most 80 bytes. At the default of 400 tables that is under 300 KB, and the public port's 120 connections can hold at most 120 such replies.
- **Pace.** `CNT` counts against the per-connection rate limit like any request, so the pages of a reply come no faster than other replies.
- **The extension channel** refuses `PAG` (`ERR NOTPUBLIC`), so nothing waits there.

## Logging

Never logged: passwords, temporary passwords, `AUT` values, session ids, sign-in keys, extension keys, the admin password, request lines of failed requests (the core logs the verb and the exception type only; the web logs the exception type and line), what players say to each other (IOS and FIBS log a typed command as typed, but only the verb of `tell`, `say` and the other chat commands, and nothing of a line that is not a command). The mail transport `log` logs address and subject only, and so does `test` (the test suite), which keeps the mails it would send in memory or in a file of the test's own. Logged: server extension names, enrollments, counts of failed `SES`, sessions ended by a key change, wrong admin passwords (with the client address).

## Attack surface

- Public: 6521 (the dial-in extension: a PROXY header, believed from a listed gateway only, then up to 15 seconds in which nothing is sent, until the first CR or LF; `PARLORNET/1` as that first line leads to the same as on 6501, and anything else to the telnet extension's login in plain text), 6501 (from a listed dial-in gateway, a PROXY header may come first; then the client's `PARLORNET/1`, within 20 seconds and with at most 10 bytes before it; then `HELO`, `USER`, `REG`, `AUT`, `CAN`, `CLI`, `MOTD`, `GAM`, `PRL`, `PAG`, `CNT` and `BYE`, with `SES`, `SRC`, `PRO`, `PRD` and `NFY` refused), 6500 (HTTP GET/HEAD/POST, 2 KB bodies), 6502, 6503, 6505, 6506, 6507, 6512, 6514, 6515, 6517 (published as 1744 too), 6518 (each adapter's login phase, then the protocol through the adapter; on 6512 it is NetSprocket's join request, on 6514 batnav's fixed 108-byte records, whose message window takes `/signin`, on 6515 it is IRC's registration and the program's introduction, then `!signin` typed in the chat; until then only IRC itself, the server's own member and its sign-in answers are served, and on 6517 NetLuff's greeting, then `/signin` in its chat box), 6513 (Play: its files, `POST /play/session` and `/play/push`, and PARLORNET/1 over the WebSocket at `/play/ws`, with the extension channel's own requests refused as on 6501), 6508 (GameMaster: the ParlorNet rulebook's `PARLORNET/1` first, as on 6501, then a sign-in relayed to the core, and its games carried inside that one connection, each belonging to the player signed in on it; a connection whose first byte is zero is read as GameMaster's fixed call record and refused, and anything else gets `ERR PROTOCOL` and is closed).
- Container-internal: 6590 (TLS handshake with any identity; after it, the full protocol plus `SES` and `SRC`; for server extensions on another host it is published on the private link's address only), 6599 (TLS handshake, admin JSON).
- Files: the database, the key directory, the settings file with SMTP credentials.

## Assumptions

- The core's process (user `parlord`) and the data directory are trusted; root on the host can do anything.
- Python 3.13+ with OpenSSL 3 (the image is `python:3.13-slim`, with Debian's CA certificates for the SMTP relay's).
- Server extensions are this project's code; a compromised server extension is contained to its own sessions and to what players type into it, as far as Containment below goes.
- The admin port 6510 is published on the host's loopback only (docs/accounts.md, deploy/install.sh); the image does not `EXPOSE` it, so `docker run -P` does not publish it. Inside the container the admin adapter listens on 0.0.0.0 (Docker forwards the host's 127.0.0.1:6510 to the container's address), so other containers on the same Docker network can reach it; the admin password, locked per client address, guards it regardless.

## Containment

**The default: one container, one unprivileged user.** The container runs as `parlord` (uid 10042, the image's `USER`; `deploy/install.sh` also says `--user 10042:10042`) with `--cap-drop ALL`, no capability added, `no-new-privileges`, a read-only root, on the isolated `parlor` bridge network (no host networking). Every process (`start.py`, parlord, the game plugins, every server extension) is that user. `/data` and the key directory are 700, the database and the keys 600 (umask 077). `start.py` logs `start: per-extension users are off: every process runs as uid 10042`. Started as root without the SETUID and SETGID capabilities it cannot switch to an unprivileged user and refuses to start (it would otherwise run everything as root), saying to use `--user 10042`.

This protects the host (no privileges, no host network, nothing writable but `/data` and `/tmp`), and the keys and database against everyone outside the container. Inside the container, though, every process can read the database (every password hash, `admin:pw`'s hash, the SMTP password if set in the menus) and every key, including `admin.key`. Code execution in any server extension therefore reaches every account and the admin socket. The key roles still hold against a stolen key file, not against a compromised process.

**Two opt-in alternatives, for the operator to choose.**

(a) **One container per process** (`deploy/install-split.sh`, deploy/README.md). The core runs in its own container (uid 10042) holding the database. Each server extension the script starts (web, telnet, IOS, FIBS, Outland, DOoM, Play and the admin menus; not GameMaster, NetSprocket, batnav, Awale, NetLuff or the bot) runs in a container of its own under its own uid (10043 to 10056, as in the image), with only its own key, mounted read-only from a host copy owned by that uid (mode 400), and no `/data`. Every container gets the same flags as the default: `--cap-drop ALL`, no capability added, `no-new-privileges`, read-only root, `--user`; no host networking. Networks: `parlor-int`, created `--internal` (no way out), carries only the extension channel (6590) and the admin socket (6599), bound to the core's address on it; the core and the extensions join it. The core's native port (6501) is bound to its address on `parlor`, which also gives it its way out to the SMTP relay. Each extension's published port sits on a network of its own (`parlor-NAME`) without NAT, bound to the extension's address there. So an extension reaches the core's 6590 and 6599 (which want its key, and the admin-role key) but not the core's 6501 or the other extensions over the internal network. A compromised server extension then cannot read the database or another key, shares no process, filesystem or loopback with the core, and is left with its own sessions; one extension's idle sockets cannot hold the core's handshake slots (per-address slots). It costs nine containers and ten networks instead of one, the admin menus' choice of server extensions is not used (the script lists them), and keys are copied by the host script. Two gaps remain (tested on Docker Desktop): Docker forwards to published ports by container address from other bridges, so an extension can reach the other containers' published ports (the ones any client reaches; 6510 among them, guarded by the admin password, locked per address); and "without NAT" stops a way out on a Linux host (replies to a private source address never come back) but not inside Docker Desktop's VM. The host firewall should drop forwarding from the `parlor-NAME` bridges to settle both.

(b) **One container, a user per process** (built; needs extra capabilities, so it is not the default). Start the image as root with `--user 0 --cap-add SETUID --cap-add SETGID --cap-add KILL`. `start.py` keeps root (with only those three capabilities) to start, watch and stop the others, and reads no network input:

| Process | User | Can read in /data |
|---|---|---|
| `start.py` (supervisor, PID 1) | root, only SETUID, SETGID and KILL | nothing (it cannot even list `/data`) |
| parlord, the game plugins | `parlord` (10042) | everything: the database (600), every key |
| each server extension | `pn-web`, `pn-telnet`, `pn-ios`, `pn-fibs`, `pn-outland`, `pn-admin`, `pn-bot`, `pn-doom`, `pn-gamemaster`, `pn-netsprocket`, `pn-play`, `pn-awale`, `pn-batnav`, `pn-netluff`, `pn-icds`, `pn-worthy`, `pn-networdz`, `pn-rscards`, `pn-dialin` (10043-10063) | its own key file only (640, group `pn-<name>`); `/data` and the key directory are 711, so it reaches its key by name and lists nothing |

A first step run as `parlord` (`start.py --prepare per-user`) sets these modes on every start, and the default mode sets them back to 700 and 600. `parlord` is a member of every `pn-` group, so `python -m parlord.frontends` run as `parlord` gives a new or rotated key to its extension's group in this layout. This protects the database and other keys against code execution in a server extension. Still shared are one kernel, one network namespace and loopback (a compromised extension can connect to 6590 and 6599 like anyone, without their keys), the others' command lines in `/proc` (no secrets are on a command line); and it needs the three capabilities, which the default does without.

**Server extensions on another host** (`deploy/install-extensions.sh`, deploy/README.md) run one container each, as in (a). Each has its own uid, only its own key mounted read-only, the same flags and no host networking. They share one network, `parlor-ext`, on which they cannot reach each other. It has a way out, which carries the extension channel to the core over the private link and lets Play reach the push services. A compromised extension there holds its own key and its own sessions, and nothing of the core's host.

In every mode the SMTP settings file is mounted read-only and must be readable by uid 10042 only; a kernel or Python sandbox escape is out of scope.

## Residuals, after the re-tests

- **Sustained guessing from a handful of addresses** (R2-1): about 4 addresses (4 IPv6 /48s) spend the server's untrusted wrong-answer budget for the day; then every player on an address they have not signed in from in 30 days (a new phone, travel, a changed mobile or CGNAT address, a return after a month) is refused sign-in even with the right password, until the budget frees (24 hours after the wrong answers) or the operator clears it in the admin menus. What still holds then: players on an address they signed in from keep signing in; recovery by mail goes ahead for a player on such a trusted address (the owners' own budget), and for anyone else only while the strangers' recovery budget lasts: strangers asking for other players' resets from about 5 addresses use up its hour (20) and from about 6 its day (60), after which a player on a new address can neither sign in nor recover until it frees or the operator clears it. Each such reset also mails a real player. Strangers' resets never use up the owners' budget.
- **A sign-in key copied without the player knowing** (a floppy lent or imaged, a browser profile copied while signed in) signs in as the player where it was given until the player forgets that computer, changes the password, or it goes `keys.idle_secs` (90 days) unused; each use keeps it alive. The profile's list shows when each key was last used, which is the player's way to notice (Staying signed in).
- **The default container is one user**: any process in it can read the database (every password hash, the admin password's hash, the SMTP password if set in the menus) and every key, `admin.key` included (Containment).
- **One container, a user per process (the opt-in)** (R2-3): every server extension and the core's channel share 127.0.0.1, so per-address handshake slots cannot tell them apart. A compromised extension flooding the extension channel with idle sockets makes the other extensions' new core connections fail at once (the web answers 503), not merely slow; measured, 5 to 11 of 20 web sign-ins got through. A loopback address per extension (127.0.0.N) would let the slots separate them; not done.
- **The split mode** (R2-4): its isolation was verified only under Docker Desktop (29.9.2, macOS), where it is weaker than designed: an extension container reaches the core's 6501 on the core's public network, other extensions' published ports at their container addresses, the admin TUI container's 6510 at its container address (published only on the host's loopback; the admin password, locked per address, still guards it), and services on the host's loopback through `host.docker.internal`. Desktop's results are not representative of Linux, where inter-bridge isolation and loopback-only publishing differ; before the split mode is recommended for parlornet.org, `review/split2_probe.py` must be re-run on a Linux Docker host (a local VM) and the host firewall's forwarding rules checked.
- **One IPv6 /48 shared by many subscribers** (R3-1): every per-address limit counts an IPv6 client by its /48 (Lockouts and rate limits). Where one /48 holds many unrelated subscribers (some mobile carriers, hosting providers), a neighbor in a different /64 can use up that /48's 12-a-day wrong-answer budget for everyone in it, and can close another subscriber's waiting login (a line adapter's pre-login places and the web's sign-in dialogs close the newest arrival of the address holding the most). This matters only when the public ports are reachable over IPv6. Counting refusals per /64 under a higher per-/48 ceiling would narrow it; not done.
- A compromised server extension can claim any client address with `SRC`, so it escapes every per-address limit for its own traffic (not the per-name lockouts or the server budgets). A custom extension that sends no `SRC` puts all its users in one `?` bucket (12 wrong answers a day between them); every shipped one sends it.
- A stranger behind a player's trusted address (a shared NAT) is exempt from the budgets for that player's name only, and is then limited by that name's own lockout (6 guesses a day).
- Lockouts can be caused by anyone who knows a name; recovery goes ahead for a name with an address on file, within the limits above.
- **An address's sign-up email can be spent by anyone who knows the address**: a sign-up naming it sends its one mail for the week (a temporary password for a name its owner did not choose, or the notice), and its owner then cannot sign up with it until the cooldown ends or the operator clears it. This is the price of the one-mail rule, which closes the old way to have the server mail someone repeatedly through sign-up (6 a day by the per-address caps, notices to an account's owner included); it now mails one person at most once a week.
- A pending account holds its name for 24 hours. Someone can hold a name, or many names up to `signup.max_pending`, for a day with sign-ups they never finish; each costs a sign-up mail within the caps, and the operator can delete pending accounts in the admin menus.
- Sign-up by email can be held up for a day from a handful of client addresses: 15 addresses (4 sign-ups each an hour, the per-address mail cap) fill the 60 places within the hour, and new sign-ups wait (`ERR BUSY`) until the places free as their 24 hours end. The same addresses could already use up the daily sign-up mail budget (finding 7). The operator's Clear budgets frees the budget but not the places; deleting the pending accounts in the admin menus frees those.
- Held mail matches a sent one's time only on average (the relay's recent send times); a requester timing many requests to a slow relay may tell some apart.
- Recovery mail for one name can be used up for a day by strangers asking from two or more addresses, for its owner on a new address (not on a trusted one).
- A sign-in with a temporary password on a client that cannot ask for a new one (Outland, NetBoxes, batnav, NetLuff) confirms a pending account but signs nothing in; the player has to use the web or telnet once. Plain text on the public ports (Out of scope).
- A long server name (up to 32) shortens or drops the operator's own label in the greeting, to keep the 80-byte line; the label is still used in the questions.

## Out of scope (accepted)

- Plain text on the public ports: 6500 (HTTP, with the cookie), 6501, 6502, 6503, 6505, 6506, 6507, 6508, 6512, 6514, 6515, 6516, 6517 (1744), 6518, 6519, 6520 and 6521 carry credentials and sessions in the clear because the clients predate TLS. An observer on the path can take them. TLS bridges for modern clients are a transport matter (docs/transports.md). ParlorNet Play is the exception when it is served through a TLS proxy (Behind a TLS proxy); published directly on 6513 without one, it is plain text like the rest.
- Browsers without cookies keep `s=<sid>` in URLs, history and screenshots for up to the session's lifetime (24 hours at most, less if idle).
- Lockouts can be triggered by anyone who knows a name, for as long as they keep guessing (denial of sign-in, at most 4 hours after each wrong answer). Recovery by mail still works for a name with an address on file; a name without one waits, or asks the operator. Recovery mail can itself be denied for a day by someone who asks for it for that name from enough client addresses (the per-name caps).
- Under `none`, anyone is anyone; under sign-up `password`, anyone may create a name.
- Second factors; hardware keys; WebAuthn.
- Login CSRF (making a browser sign in as the attacker).
- Per-address limits trust the address a server extension passes (`SRC`); a compromised extension can lie about it, which only affects limits on its own traffic. Behind a shared address (a school, a carrier NAT) players share those limits. Where Docker's userland proxy forwards IPv6 to the container, all IPv6 players appear as one address.
- A well-formed Host header (a host name or address, an optional port) is used for the web's redirects; nothing else a client sends is.

## Review findings and fixes

An adversarial review of this design and its code (branch `sessions` at 3dbbf5d) found the items below. Its reproductions are in `review/` (`python3.13 review/r1_extension_exhaustion.py` and so on; R1 needs `ulimit -n 8192`); `tests/test_review_fixes.py` has a test class for each item (`F01...` to `F15...`).

| # | Severity | Finding | What changed |
|---|---|---|---|
| 1 | High | IOS and FIBS opened a core connection for every TCP connect, before any login, and counted only signed-in players, so about 400 idle connects from one address filled the core's single extension-channel cap and shut out every server extension. | IOS, FIBS, telnet and Outland open their core connection only once the client has sent a login line (telnet fetches the message of the day over a short shared connection, at most once a minute). `common.Gate` counts each adapter's clients that have not signed in: at most 20, 4 from one address, 2 minutes to send the login line and 10 to finish signing in; signed-in players have their own cap. The web caps requests per address (20) and sign-in dialogs (finding 6). The core gives each server extension its own share of the extension channel (250 connections per key name, 1200 in all, 32 in the TLS handshake), so a flood through one cannot starve the others. |
| 2 | High | SMTP STARTTLS without certificate verification: anyone on the path to the relay (or answering for its name) got the relay credentials and every mail, so any account with an address on file could be taken over through `reset`. | `ssl.create_default_context()` for STARTTLS (and implicit TLS on port 465 or with `email.smtp_tls=tls`): the chain is verified against the system's CA certificates and the relay host (`email.smtp_host`) is the TLS server name. A relay without STARTTLS, or whose certificate does not verify, gets nothing; the step is refused (`ERR NOMAIL`). `email.smtp_ca_file` adds a CA of the operator's own. The image checks at build time that the CA bundle is there. |
| 3 | Medium | Wrong codes at the recovery steps (the mailed password-reset code, and the re-enrollment of the app-code sign-in method, since removed) did not count toward the lockout; each mail gave 5 free guesses. | Every code check counted toward the name's lockout, with mailed codes of 8 digits and 3 tries each, and mails per name at 2 an hour and 4 a day. Recovery now mails a temporary password of about 59 bits, and every wrong one counts like a wrong password (Lockouts and rate limits). |
| 4 | Medium | Lockouts never decayed (one guess a day kept a name locked for good) and blocked the player's own recovery. | The count halves after each 8 hours without a wrong answer; the longest wait is 4 hours (was a day). While a name with an address on file is locked, the question is still asked with a note, and only `reset` (recovery by mail, with its own limits) is accepted. |
| 5 | Medium | Email sign-up said which name owns an address (`ERR EMAILINUSE ... alice`). | An address that already has a name gets a notice mail to its owner, and the dialog goes on exactly as for a free address (the same lines, the same caps; no code can finish it), so it never tells whether or to whom an address belongs. The notice counts as sign-up mail; recovery mail to an address counts only recovery mail to it, so notices cannot use up the owner's recovery. |
| 6 | Medium | 100 anonymous POSTs filled the web's 100 sign-in slots for 15 minutes. | At most 4 sign-in dialogs per client address; a dialog waits 5 minutes for its next answer (was 15); when full, the oldest is ended instead of refusing new ones. The core also limits sign-ups per client address (finding 13). |
| 7 | Medium | Email availability: one shared server-wide budget for sign-up and recovery, no per-source caps, and 4 bounced addresses held every new sign-up until the operator acted. | Per-client-address caps (4 an hour, 10 a day; the web and every adapter pass the address with `SRC`, the public port uses its own). Separate server-wide budgets for sign-up and for recovery. Bounces are counted by who asked for the mail: a client address with 2 bounced addresses in a day gets no more sign-up mail that day; the hold on all sign-ups needs bounces from more than 3 requesters; recovery mail to addresses on file is never held. |
| 8 | Medium | Containment existed only on paper: every process in the container ran as one user, so code execution in any adapter could read the admin key, every key and the database. | Described under Containment. The default stays one unprivileged user with no capabilities (database and keys 600, directories 700), and says so in the log. Two opt-in alternatives are offered for the operator to decide: one container per process (`deploy/install-split.sh`, no extra privileges) and a user per process in one container (needs SETUID, SETGID and KILL). |
| 9 | Low | A newline in a web form answer became a second protocol line on the extension channel. | `CoreClient.req` refuses any request with a control character (CR, LF, NUL, DEL and the rest), for every adapter; the web shows "That has characters that cannot be used". Validation regexes end in `\Z`, not `$`. |
| 10 | Low | Rotating or removing an extension's key did not end the sessions it was issued. | Sessions store the issuing key's fingerprint; `SES` with another key fails and ends the session, and every sweep ends the sessions of a rotated or removed key (also after a restart). Sessions stored before this change have no fingerprint and end at their first resume. |
| 11 | Low | The web's per-address resume limit deleted the cookies of everyone behind the same address. | Past the limit, a session id that has resumed through this web before is still tried, and the cookie is no longer cleared when the limit stops a resume. |
| 12 | Low | A deleted player's seats, running games and private tables passed to the next account with the same name. | Deleting an account ends its running games (`END abandoned`), gives up its seats at open tables (a table left empty goes), clears its ownership, and removes finished private tables it played at, besides withdrawing its invitations. |
| 13 | Low | Unlimited scrypt work during sign-up. | A chosen password is held as a keyed HMAC until its confirmation matches and is hashed once then; at most 2 scrypt hashes run at once; one client address may start at most 20 sign-ups in 10 minutes. |
| 14 | Low | The raw Host header went into `Location` (a bare LF split the header). | A request with a bare CR or LF (or NUL) in any line is refused (400). Redirects use the Host header only if it is a well-formed host name or address with an optional port, else the default name. |
| 15 | Info | Smaller items. | Non-ASCII in a code or the admin setup password is a wrong answer, not an internal error (`auth.same` compares bytes). The greeting shortens or drops `LABEL` to fit 80 bytes; `MOTD` lines are at most 73 characters and long words are cut. The SMTP password is listed under Data at rest (the settings file is preferred). IOS and FIBS log commands but not chat text or non-command lines. The IOS docstring now says the password answers only a `cred` question. The image no longer `EXPOSE`s 6510 (the admin adapter listens on 0.0.0.0 inside the container so Docker can forward the host's loopback to it; see Assumptions). Wrong admin passwords lock the client address they come from, with the same decay, not everyone. The operator's one-time password works for 24 hours (now a temporary password, as every mailed one). `python -m parlord.frontends` refuses names that are not extension names (no paths). |

The default deploy (`deploy/install.sh`) adds no capability: `--user 10042:10042 --cap-drop ALL --security-opt no-new-privileges`, as before.
