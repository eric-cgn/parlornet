# Trust: what clients and server extensions may decide

ParlorNet trusts one thing, the core (parlord): it runs every game, and its word is final. Everything else, a frontend on a player's machine or a server extension that speaks a period protocol, is a client of the core and is believed about nothing but the player's own choices. Below are the rules every frontend and server extension follows, each service checked against them, and the gaps. Sign-in, sessions and the extension channel are in [security-design.md](../security-design.md).

## The rules

1. **The core is the only authority.** Game state, legality, scores, results, clocks and who a player is all belong to the core. A client or an extension is never believed about any of them: every move goes to the core (`MOV`), which accepts or refuses it, and what a client shows afterwards comes from the core's answer, its view (`VUE`) and its events. A result a period client works out for itself is not passed on. A game is played by programs nobody here wrote or can check, from machines nobody here controls; if any of them could say "this is the board" or "I won", the weakest client would decide every game.
2. **Randomness comes only from the core.** Dice, shuffles, the bag, deals and random placements come from the table's seed, which the core draws from the system's secure generator, 63 bits wide, when the table is made (`parlord.core.table_seed`, tests/test_trust.py). The game plugin keeps the seed in the state and never puts it in a view or an event ([plugins.md](../plugins.md)). No option a client sends replaces it, except where a game says so in its type spec and this note lists it (Exceptions, below). A player who chooses or predicts the dice wins, and a seed too narrow could be found by trying every value against the dice or tiles already seen.
3. **Hidden information stays in the core.** Racks, fleets and the bag are kept in the state; a client is sent only what its player may see: its own view, and events that every player and watcher may see. Where a period protocol needs a client to hold more (a program that works out the result itself), the core sends it only for that ruleset, and the exception is documented where it happens: in the type spec and in the server extension's notes, and listed here. Whatever reaches a player's machine can be read there, by any program.
4. **Identity comes only from the server's sign-in.** A connection is a player once the core's sign-in method has said so ([accounts.md](../accounts.md)); a server extension relays the steps and holds the session the core returns. Nobody is anyone because of their address, a machine name or a name the client sends unasked. The exceptions are a LAN or a festival, where the operator chooses sign-in `none` and anyone may be anyone, and any other case documented here. Client addresses are used for limits (how many sign-ups, how many wrong answers), never to say who someone is, because addresses are shared, reused and forged, and a name typed into an old program proves nothing. The same goes for what a client says it is: the program and the machine it names with `CLI` ([protocol.md](../protocol.md), Clients and machines), or that a server extension names for it, are a label the server records with each turn and shows in a table's history, the activity and the player's profile, and tells a table when the player sits down (`CLIENT`), and nothing more. The server cleans the text (printable ASCII, at most 40 characters) and never uses it to decide who a player is, what they may do, which rules apply or which hidden information a connection gets; any program can say it is NetBoxes on a Macintosh. The game's own words for a turn (`say`, [plugins.md](../plugins.md)) come from its public events only, so the record gives nothing hidden away. A private table's programs and machines go only to the players seated there, and what each player plays with (`CLIENT`) only to them and the table's creator; anyone else watching sees the seat and not the program.
5. **Where a period protocol gives a client authority, ParlorNet takes that role itself.** Some protocols make one machine the host, which deals, keeps the bag or checks words. ParlorNet always plays that machine, so the host is the core: NetBoxes, for one, always joins, with the server as host. A client that keeps some authority anyway (its own word check, its own board, its own count of hits) is reconciled to the core, and the core wins. When they disagree, the server extension takes back any steps of the turn it already made, so the core's game is as it was; brings the client back to the core's game by the protocol's own means (a fresh board, the turn handed back with the core's board and dice, a full game state that overwrites the client's); and tells the player in words, in the client's own message window or chat, what was refused and why. Where the protocol has no way to bring the client back, it leaves the game running in the core and tells the player where to finish it (the web or telnet). The player has to see the game the core is playing; a client left showing a different board would invite moves the core then refuses one by one.
6. **Clients may check things locally for convenience, but the server decides.** A program may mark legal moves, check a word against its own dictionary, preview a score or refuse a move it knows is illegal; `CHK` asks the core the same question without playing. None of that is final: a move the client let through can still be refused, and the core's view replaces anything the client worked out. Checking locally saves a round trip on a slow line, and many period programs do it; it must never turn into the client deciding.
7. **Extensions relay.** A server extension turns the period protocol's requests into core requests and the core's answers into the period protocol. It never decides a game's outcome itself, never plays for a player beyond what that player asked for, never keeps a credential longer than the sign-in (only the session handle the core returns), and never sends a credential anywhere it was not asked for: a password the client supplied answers only the core's credential question ([security-design.md](../security-design.md#what-each-server-extension-may-and-must-do)). An extension is one more program between the player and the core; the less it decides, the less there is to get wrong or to attack.

## The services against the rules

In every row the moves are checked by the core (`MOV`), and scores, results and clocks are the core's.

Notes:

- **Web and telnet** keep no game of their own. Each page or screen is drawn from the core's view, so there is nothing to reconcile.
- **IOS** clients redraw the whole board from each board record, so a refused move is put right by the next board; the client's own move check is convenience (rule 6). Choosing a color at random for a challenger who left it open is a seating choice the challenger could have made, not chance in the game.
- **FIBS** reads a move such as `8-2` with a double as the steps it stands for, by asking the core's list of legal steps; a turn is played whole or not at all.
- **Outland Backgammon** offers the cube before the roll, which the core cannot do once it has rolled, so an Outland player's double is refused with a message and the turn handed back.
- **Outland Reversi** plays its own move on its board before the core answers. A refusal means the two already disagree (a faulty or modified client, or a move after the game moved on); the board is then set aside rather than played on, since the protocol cannot take a move back.
- **GameMaster** was written for two Macs that both run the rulebook and trust each other. ParlorNet is the remote Mac, reached only through the ParlorNet rulebook's connection: each move from the caller's Mac is played in the core, and the other side's moves are sent to the Mac from the core's events. The Mac's own result is never passed on. A saved game in progress is turned down, so every table starts from the beginning in the core.
- **ParlorNet's own GameMaster rulebooks** (rulebooks/checkers, mancala, fiveinarow, gridwords, rummytile, cannonfire and backgammon in the eric-cgn/parlornet-gamemaster repository) follow the rules by design: the Mac sends a whole move (`M`), the extension plays it in the core, and the Mac draws it only when the answer `A` comes; a refusal comes as `R` with the core's reason. The other player's moves and the end of the game come from the core's events. Between two Macs, outside ParlorNet, each copy checks the other's moves instead; Grid Words, Rummy Tile, Cannon Fire and Backgammon, which need a dealer, the core's physics or its dice, play only on a parlor. In Backgammon the Mac stages a turn by the same rules and sends it whole; the extension plays its steps in the core and takes them back if any is refused, and the Mac draws the board from the core's view after every change. In Rummy Tile each step of a turn is played in the core as it is made, and the Mac draws the table and its rack from the core's view after each. A game being played can be taken up from GameMaster (Resume): only a table where the signed-in player has a seat, with nothing at it changed, and the Mac is sent the position from the core's view of that seat before any move.
- **The bot** is a client like any other. It imports the game's rules only to look ahead.

## Exceptions in force

Each exception is written down where it happens as well as here.

- **The other fleet in Naval Combat's salvo ruleset.** GameMaster's BattleShips works out the hits on the Mac, so at a Naval Combat table with the `salvo` ruleset each seated player's view carries the other fleet (`OF` lines) once both fleets are ready; watchers never get it ([navalcombat-1.md](../types/navalcombat-1.md)). The web, telnet and the bot do not show or use it, but a program reading the view can.
- **Every rack and the bag for a Networdz player's program.** Networdz's protocol sends the bag and every rack to each player's program, so the Networdz extension reads them with `VUE table O` and passes them on. The core gives them only on the extension channel, to a seated player, at a table the extension has marked `integrity=false` ([protocol.md](../protocol.md)); the mark shows in the table list, the view, the notes and the table's log. The parlor still deals, judges every word and ends the game, and Networdz shows its player only their own rack.
- **Cannon Fire's seed option.** A table's creator may give the seed of the landscape and the wind, so a known landscape can be replayed ([cannonfire-1.md](../types/cannonfire-1.md)).
- **Sign-in none.** For a LAN or a festival: a name alone signs in, and anyone may be anyone ([accounts.md](../accounts.md)).

## Gaps

Places where a client can still affect state, randomness or identity in a way the rules above forbid, each with a proposed fix awaiting a decision.

1. **The other fleet goes to every program at a salvo table.** The exception is for GameMaster, but the core cannot tell a GameMaster player from anyone else, so a native client at a `salvo` table reads the other fleet while a web or telnet opponent sees nothing. Proposed fix: send `OF` only when every seated player's frontend needs it, by a flag the GameMaster extension sets when it seats its player (for example a table option `openfleet=1` that only `salvo` accepts, shown in the table list and on the web and telnet before anyone sits down), so a player always knows the fleets are open.
2. **Cannon Fire's seed option lets a table's creator choose the landscape and the wind.** A creator can pick a seed whose landscape favors one seat and sit there, and knows every change of wind to come. Separately, the landscape is public and comes from the same 31-bit generator as the wind, so a program that tries every seed against the landscape can predict the wind. Proposed fix: accept `seed=` only with `wind=0` and show it on the table before anyone sits down; and in a next version of the type, draw the wind from a second generator whose seed the landscape does not reveal.
3. **A refused GameMaster move resigns the game, and the Mac is not told why** (the User Kit rulebooks; ParlorNet's own rulebooks are told and play on). The core does win, but the player loses a game that could go on, and sees only the hang-up. Proposed fix: as Outland Reversi does, leave the game running in the core and tell the player where to finish it, with a GameMaster message before the hang-up if one can be shown.
4. **Outland Backgammon plays the rest of a turn for the player.** After the client sends an incomplete turn three times, the extension plays the first legal steps from the core's list and ends the turn. Every step is still the core's to accept, but the extension chooses moves the player did not make. Proposed fix: hand the turn back with the message each time and leave the rest to the turn clock.
