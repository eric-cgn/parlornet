# Server extensions (draft 0)

There are two kinds of server-side plugin, kept apart:

- **Game plugins** (plugins.md): rules for one game type, run as a subprocess of pure functions.
- **Server extensions** (this file): programs on the server side that each speak one protocol to frontends, the programs players use (a browser, a telnet program, a 1990s game client), and the client protocol (protocol.md) to the core. They sit in the transport layer of architecture.md and connect to the core's trusted port for server extensions. They never touch game plugins, and the core never learns that a player came through one. Players see them as the supported protocols (protocols.md, on the docs site as `/docs/protocols.html`).

Server extensions live in the `adapters/` package (`adapters/*.py`), and the code calls them adapters. The native protocol on 6501 has no extension: the core serves it itself.

## Declaring the protocol

Every server extension that players connect to declares its protocol to the core (docs/protocol.md, Protocols; docs/design/protocol-declarations.md). Its module has `PROTOCOL = (key, name, description)`, and its `serve()` calls `declare.start(args, PROTOCOL)` (adapters/declare.py) once it listens: one connection to the core is kept open for `PRO key port name` and `PRD key description`, sent again every 5 minutes, and made again if the core goes away. The port is `--public-port` when the extension is published under another port than it listens on (Outland: 4000 in the container, 6506 on the host, which deploy/start.py passes from `catalog.PUBLISHED`; GameMaster: 6508, or another number where the host publishes 6508 under it and sets `PARLOR_GAMEMASTER_PORT`, which deploy/start.py passes on), else `--port`. The core lists the protocol while that connection is open, and the web's Protocols page shows it. The admin console and the bot declare nothing.

## Saying what the player's client is

The core records with each turn the program and the machine the player's connection named with `CLI` (docs/protocol.md, Clients and machines), and shows them in a table's history, the activity and the player's profile. A server extension knows better than anyone which program is on the other end, so it says it for the player it serves, on that player's connection to the core, with `CoreClient.claim(program, machine)` (adapters/common.py), which cleans the text as the core does and carries on quietly when a core is older than `CLI`. The names come from the clients catalog (adapters/clients.py) where it has one.

| Extension | Program | Machine |
|---|---|---|
| NetSprocket | NetBoxes 1.1, known by the program's first message | Macintosh |
| GameMaster | what the ParlorNet rulebook sends, such as GameMaster 1.0.0 + ParlorNet 0.4; GameMaster and the version from the call record for an older rulebook | the Mac's model from Gestalt, such as Macintosh SE/30; Macintosh for an older rulebook |
| FIBS | the client named on a CLIP login line (`login MacFIBS_3.0.6 1008 ...` is MacFIBS 3.0.6); nothing for a `connect` login, which the CLIP specification offers every client, or for a login by name and password, which every FIBS client and telnet program use alike | nothing |
| IOS | nothing: an IOS login carries only a name and a password | nothing |
| Outland | Outland Gateway | Macintosh |
| batnav | what the client's BNJUG record names, with batnav before it: batnav xbtclient 0.50, batnav nbtclient 0.50, batnav btwin 0.48, batnav gbnclient 0.60 | Windows for btwin; nothing for the others, which run on any Unix |
| NetLuff | NetLuff and the version its `ip` message claims, such as NetLuff 1.4.0 | Macintosh |
| Worthy Opponent | Worthy Opponent and the version of its handshake, such as Worthy Opponent 2.0 | IBM PC |
| Telnet | telnet and the terminal type the player's program gave (telnet TTYPE), such as telnet (VT100); telnet when it gave none | nothing |
| Web (1997 pages) | the browser and its version from the User-Agent, such as Netscape Navigator 3.0, by a small table in `adapters/web.py` (`UA_BROWSERS`); an unknown browser is its first word and version, and no User-Agent names nothing | the platform from the User-Agent, such as Power Macintosh, Windows 95 or Amiga (`UA_MACHINES`) |
| Play | the page says it itself over its WebSocket: ParlorNet Play in the browser and its version, such as ParlorNet Play in Firefox 132 (docs/modern-client.md) | the system, such as macOS or iPhone |
| Awale | Awale | nothing: the introduction line does not say whether it is the Mac or the Windows version |
| ICDS | nothing: a login carries only a name and a password, and xcheckers sends nothing that names it | nothing |
| Networdz | Networdz 2.0: only 2.0 plays over a network, and its messages name no version | Windows |
| RSCARDS | RSCARDS and the version its identification line gives, such as RSCARDS 5.02 | the machine its code gives: IBM PC, Macintosh, Commodore 128, Amiga, Atari ST or Apple IIgs |
| Bot | ParlorNet bot | nothing |

The web pages send it with each request that plays a move, since each of their requests is a connection of its own. Only what is known is sent: where a login does not name the program, as on IOS, on DOoM (BobGrid or a telnet program) and in FIBS's `connect` and two-line logins, nothing is guessed from how a client behaves. None of this is believed about anything else (docs/design/trust.md).

## Web extension: 1997 and 2027

- **1997:** server-rendered HTML 3.2 for any browser with tables, forms and image maps (Mac Mosaic 2.0 and later; the Browsers page lists them): tables, forms, links and small GIFs only, no CSS (a little optional JavaScript polls for changes). Sign-in runs the server's steps through POST forms; the session the core issues is kept in a cookie, or in links (`s=`) for a browser that returns no cookie (docs/accounts.md, docs/security-design.md). No credential is ever in a URL or a page. Pages end in `.htm`. A game's board is one GIF drawn on the server (`/board.gif`, cached by the browser while the board is unchanged) with an image map: client-side (`USEMAP`) and, for older browsers, server-side (`ISMAP`, `/click.htm`); docs/games-howto.md has the details. Connections may be kept alive for a few requests (HTTP/1.0 `Connection: keep-alive`, HTTP/1.1). Every game is built, with click-to-move.
- **2027:** a modern site on the same port, a JSON API under `/api/` with the same typed views as JSON, and canvas, WebAssembly and WebGL clients on top of it. It is not built yet, and `/2027/` is reserved.
- The welcome page lets the visitor choose. Both sides are clients of the same core through the same extension code.
- Profiles and the activity: every player's name in the lobby, at a table and in the activity links to their profile (`/player.htm?who=name`, from `PFL` and their latest public turns from `FEED n name`), where your own has a link to set your preferred machine (`/profile.htm`, `PFL SET PREF`). A table's log ends each turn's line with what it was played with, where the core's `TRN` gives that to the viewer. Activity in the navigation bar (`/activity.htm`) lists the latest 20 turns at public tables as sentences, such as "eric played FRAULEIN for 65 in Grid Words with BobGrid 2.3 on a Sun SPARCstation". docs/site.md has the pages.
- The leaderboard (`/leaderboard.htm`, from `TOP`, which needs no sign-in): the players with the most points, by every game or one, with the note that any score is easy to get on a public server and that the leaderboard is meant for conferences, festivals and LAN parties. The welcome page and the lobby link to it, and a profile shows the player's score and rank (`PFL SCORE`). While the operator has the leaderboard off (`scores.show`), the page is not found and no link or score shows. docs/site.md has the page.

## Play extension

ParlorNet Play (docs/modern-client.md), the client for today's browsers, is a server extension of its own, `adapters/playserver.py`, on port 6513, with its own key and, in the per-user layout, its own user (`pn-play`, uid 10055). The operator turns it on or off like any other (the admin menus' Adapters, `adapters.enabled`, `PARLOR_ADAPTERS`), and the web extension and Play each run without the other. It serves the files of `adapters/play/`, the WebSocket at `/play/ws` (adapters/wsbridge.py; docs/protocol.md, WebSocket), `POST /play/session`, which sets its own session cookie, and `POST /play/push`, for push notifications (docs/play-notifications.md), which it sends from the core's notices (`NFY`) when `play.public_url` is an https address and `play.push_contact` (`PARLOR_PLAY_PUSH_CONTACT`) is set; it keeps their subscriptions and its VAPID key in its own data directory (`--data`). It declares `HTTPS`, at the port of `play.public_url` when that is set (443 for an https address), else its own.

It speaks plain HTTP and expects a reverse proxy in front that terminates TLS (deploy/README.md). `play.public_url` (`PARLOR_PLAY_URL`) is the address players open; `play.proxies` (`PARLOR_PLAY_PROXIES`) lists the proxies whose `X-Forwarded-For` and `X-Forwarded-Proto` it believes (docs/security-design.md, Behind a TLS proxy). Both are read from the settings file or the environment at start. The web extension learns from the core's `PRL` whether Play runs: then its welcome page links Play, and `/play` answers with a 301 to `play.public_url`, or a short page linking Play's port; without Play and without a public URL, `/play` is a 404 that says Play is not offered here. In the same way Play learns the web extension's port from `PRL` and links the classic pages only while they run.

## Telnet extension

One telnet server serves the whole game server, not one per game.

- Login by handle (as `HELO`), a menu built from `GAM`, then the table list from `LST`, with join or create.
- Per-type renderers: each game type has an 80x25 ASCII reference rendering (the rule in protocol.md); ANSI terminals get color and cursor placement as an enhancement. A renderer reads the type's typed view and events and draws the screen; it contains no rules.
- Terminal capability is negotiated or asked at login (plain 80x25, ANSI, narrower).
- It runs beside the server, is not part of it, and an operator may leave it out.

Built (adapters/telnet.py): the screen is 80x24. The terminal type (telnet TTYPE) picks a default display mode, offered in a menu with a sample line per mode: `pc` (ANSI color, IBM PC CP437 characters; the default when no type is sent), `utf8` (the same characters in Unicode), `ansi` (color, ASCII only) and `plain` (no escape codes).

- ANSI modes are full screen. The main menu has a title bar, a "Your tables" panel (opponent, time per turn, whose move and time left), an "Other tables" panel and a "Start a new ... table" entry per game (Reversi, Backgammon), chosen with the arrow keys and Enter; a status bar lists the keys (N new table, with a game picker when no new-table entry is selected, then a time-per-turn picker of 5m, 15m, 1h, 1d, 3d or 5d; W watch, P password (under sign-in password: the server's change steps), O options (the movement keys), ? help, Q log off after a Y/N confirmation; R refresh is in the help).
- The Reversi screen draws the board with double-line frame and single-line grid (ASCII in `ansi` mode), dark discs `▐█▌` and light discs `▐▓▌` (X and O in ASCII) on green, a cursor cell, legal-move dots on your turn, and a side panel with players, disc counts, whose move, the turn clock and a log. Arrow keys move, Enter or Space places, T talks, R resigns after a Y/N confirmation, Esc goes back to the menu and the game goes on.
- The Backgammon screen draws the board as character art in a wooden frame: 24 points as triangles (CP437 blocks in `pc` and `utf8`; `#` and `:` fills with `\ /` edges in ASCII), checkers `(█)` and `(▒)` (`(O)` and `(X)` in ASCII; white is seat 0) stacked on the points (a stack taller than 7 shows 6 checkers and `+n` for the rest in the seventh place, as does the bar), the tray with borne-off checkers and the cube (on its owner's side), the dice still to play on the mover's side, and a side panel with players, pips, borne-off counts, whose turn and the phase, the dice, the cube, the turn clock and a log. Your side is at the bottom with your home board on the right. A player who prefers it on the left presses H (or types `home left`; `home right` puts it back) and sees the mirror image, with points 1 to 6 at the bottom left and the tray beside them; the points keep their numbers, moves are typed the same, and the left and right arrows still move the way they point. The choice is kept with the player in the telnet extension's own data on the core (`PRF bghome`). Arrow keys move a cursor over the points, the bar and the tray; Enter or Space picks up a checker that can move (the cursor goes to its nearest target, and all its targets are marked) and Enter on a target plays the step (`MOV`); U undoes a step (`UND`), E ends the turn (`END`; Enter too, once nothing is left to play), Enter rolls, D doubles, A takes and P drops (after a Y/N confirmation). T talks, R resigns and Esc goes back to the menu, as on the Reversi screen; the status bar shows the keys that apply. Typed moves are `13-9`, `bar-22`, `6-off`, `roll`, `double`, `take`, `drop`, `undo`, `end`.
- Mouse: when the terminal type is one that reports the mouse (xterm, screen, tmux, rxvt, PuTTY, iTerm, Alacritty, kitty, Konsole, GNOME Terminal, WezTerm, foot; not the Linux console), full-screen mode turns on click reports (DECSET 1000 with SGR coordinates, 1006; the older `ESC [ M` form is read too) and turns them off again on leaving. A click selects a menu row (a second click opens it), plays a legal Reversi square, picks up a Backgammon checker and puts it down, picks an option or a button in a dialog, and presses a status bar key. Arrow keys work everywhere without a mouse.
- What each player plays with (the core's `CLIENT` event; docs/protocol.md, Clients and machines) shows wherever telnet tells who sat down. In a table's log a player's sitting down reads "ann sat down with GameMaster 1.0.0 + ParlorNet 0.5 on a Macintosh Plus", wrapped to the log's width, and a player who comes back with another program reads "ann now plays with ...". When a table opens, the log says what each other player plays with if the events it shows do not (`VUE table C`). The menu's line under the tables names the selected table's players with their programs, cut to fit ("Table 5: ann (with GameMaster 1.0.0) waits. Enter sits down, W watches."), and the plain menu puts a line under an open table and under each of your own tables for each player whose program is known (`LST clients`). Where the server says nothing, as for a player whose program named nothing or for a watcher at a private table, nothing is shown.
- Typed commands still work in every screen (`join 1`, `new 5m`, `d3`, `say hi`, `quit`): a hotkey letter followed at once by more typing counts as typing.
- Movement keys, for terminals that send no arrow keys: a session's choice of IJKL, ESDF, WASD or HJKL (vi), made with O in the menu, or at the login when the terminal type is unknown or VT52-class (K at the "Press Enter for the menu" prompt). The arrows work in every choice, and the default is the arrows only. On an empty line the four letters, either case, move the cursor in the menu, the pickers and every board and never act as hotkeys. `:` opens the command line, where every letter types; `:` then a hotkey letter does what that key does (`:d` for D under WASD). The status bar shows the letters in place of "Arrows" and such keys as `:d`, and the help box starts with the letters. In Grid Words every letter types once Enter has set a word's start. The choice is kept with the player in the telnet extension's own data on the core (`PRF`, docs/protocol.md) and comes back at the next sign-in.
- Screens are composed as a grid of cells and only changed cells are sent, with short color changes; a cursor move costs about 100 bytes and a clock tick about 25, so 2400 baud is usable. No line feed is sent and the bottom-right cell is never written, so the screen never scrolls.
- `plain` mode is line by line with a prompt; moves are typed (`d3`, `13-9`). Backgammon prints the same ASCII board with the players, dice and cube beside it, mirrored after `home left`.
- Profiles: `profile [name]` (also `finger` and `whois`) shows a player's profile, or your own: the preferred machine, the games played and the programs and machines used at public tables, and the latest three public turns; in a box on the full screen, as lines in `plain` mode. `machine [text]` sets your preferred machine (asked for when left out; `machine -` clears it), and `activity` shows the latest five turns at public tables as sentences.
- Scores: `scores [game]` (also `leaderboard` and `top`) shows the leaderboard, the first ten players with their points, wins, draws, losses and resignations, in every game or in one (`scores reversi`), and the note that any score is easy to get on a public server, since the leaderboard is meant for conferences, festivals and LAN parties. A profile shows the player's score and rank. While the operator has the leaderboard off, `scores` says the server shows none and profiles show no score.
- Time: `time` shows how long the player has been connected (since signing in on telnet) and the server's time in UTC, from the core's `TIM`: "Connected 12:34. Server time 21:05 UTC."
- The menu lists the player's invitations. The plain menu shows them under "Invitations for you". The full-screen menu shows them at the top of Your tables and gives a notice when a new one arrives. Enter or `join n` accepts an invitation, and `X` or `decline n` declines it. At a table, `invite name` invites a player, `uninvite name` withdraws the invitation, and `bot` invites the bot. The table's log says how each invitation ended. `who` lists the players who are online.
- Leaving a table or disconnecting never resigns; only `RES` or the turn timer ends a game early.

## Admin console (operator extension)

`adapters/admin.py`, on port 6510: the operator's menus (docs/accounts.md, admin panel), over telnet. It reuses the telnet extension's terminal handling, cell screen and line drawing, and draws dialog-style screens: a blue background with a title line and a key hint line, gray boxes with a light top-left and dark bottom-right edge and a shadow, sunken lists, `< OK >` buttons with the active one highlighted. It has menus, checklists, radio lists, one-line inputs (hidden for passwords), a multi-line editor for the message of the day and message boxes, and takes arrow keys, Tab and Shift-Tab, Enter, Space, Esc and the first letter of an item or button. Before the first screen it asks for the display (pc, utf8 or ASCII), as the telnet extension does.

It is a client of the core's admin socket (127.0.0.1:6599: TLS 1.3 with an admin-role key, then the admin password) and has no power of its own; at most 4 sessions at a time.

## Which server extensions run

`adapters/catalog.py` lists the server extensions a parlor can run, the admin console included, with their ports. The admin menus store the choice (the Adapters menu; setting `adapters.enabled`); the container's start script (`deploy/start.py`) reads it before starting anything and starts those that are installed, then parlord. With no choice stored, `PARLOR_ADAPTERS` or else every installed extension runs. If any process exits, the container exits and Docker restarts it.

## Game-network extensions

Many games already have a network mode or a community server with its own text protocol. Where it makes sense, a server extension lets existing clients of that network play on our server, using our game types underneath.

- A game-network extension is specific to a game type (for example Reversi) and to one foreign protocol. It maps the foreign commands and login onto client-protocol requests, and our events onto the foreign output.
- Foreign identities become handles in `HELO` terms. Anything the foreign protocol has that we do not (ratings, rooms, tells, channels) is either mapped to an optional capability or left out; the extension documents what it drops.
- First target: the Othello-server protocol used by Reversi "The Eclipse" ("IOS"), in `adapters/ios.py`. Its output follows what Eclipse 1.2's code parses: login ends on the first `<ios>` line, `who` in Eclipse's columns, listing the players who are online on any frontend and the bot, `<ios> [name(-) connected` and `disconnected` lines as players come online and go idle or leave, `[GAME n ...] created/ended` for every game, `PB` board lines, `match name` as an invitation through the core on a table made for it, invitations from anywhere as `MATCH ... FROM` offers that `accept` and `decline` answer, tells as `name: text`, and `ob`/`board <n>` for watching. Sign-in and sign-up run in the client's window before the lobby (docs/accounts.md, the dialog): the name alone goes to the server, the IOS password answers its credential question (and is dropped if none comes), and every other step, a whole sign-up included, is a prompt with the server's own label; ratings are left out (games are unrated).
- Second: Backgammon for clients of the First Internet Backgammon Server (FIBS), in `adapters/fibs.py` on port 6505. Below.
- Third: Backgammon and Reversi for the Outland Gateway (Mac, 1994-95), in `adapters/outland.py`. The Gateway talks a binary framed link (sequence and ack numbers, DLE stuffing, a keyed 16-bit check) with a control channel and up to three game channels; Backgammon uses fixed 258-byte records. The extension speaks the link, signs the player in with the Gateway's account name and password (the password answers the server's credential question; a password the server mailed is refused with a pointer to the web or telnet, where the player first chooses one of their own; the login only signs in, so a name with no account is refused with a pointer to the web and telnet; a refusal shows a text window and then the Gateway's own "account not found" or "password incorrect"), lists Backgammon and Reversi as its services, and maps the lobby, challenges, the server's dice, moves, doubles offered by others, resigning, chat and the end of the game onto `backgammon/1` tables. Outland Reversi 1.1.1 runs on another channel of the same connection. The extension maps its waiting room, invitations, moves and passes, talk and the end of the game onto `reversi/1` tables. The client checks moves itself and counts them to know whose disc comes next, so the extension sends it the opponent's moves and passes and never its own. Its board is the web's board mirrored left to right. Players type the parlor's host and port 6506 into the Outland TCP Tool's settings (the tool's port field is editable; the extension's own port is 4000, as Outland's was). The lobby lists the players who are online and the bot. A challenge to another Outland player is relayed to them. A challenge to anyone else becomes an invitation through the core, and an invitation from anywhere reaches the Outland player as a challenge. Watching, draws, high scores, Reversi's Hall of Fame, account creation and software downloads are left out, and an Outland player's own double is refused because the client offers the cube before it shows dice the server has already rolled.
- Fourth: Grid Words for the clients of DOoM, John Chew's crossword-game server (1993 to about 2005), in `adapters/doom.py` on port 6507. Below.
- Fifth: Dots and Boxes for NetBoxes 1.1 on the Mac, over Apple's NetSprocket, in `adapters/netsprocket.py` on port 6512. Below.

## FIBS extension (port 6505)

It speaks FIBS's plain-text ("telnet") mode, which MacFIBS 3 (and 2.0.3 before it), FIBS/W 1.30, xfibs 0.8 and xibc 0.31 parse, and CLIP for later clients.

ParlorNet is not FIBS: the First Internet Backgammon Server still runs at `fibs.com` port 4321, with its own community and ratings, and ParlorNet is not affiliated with it. The extension takes from FIBS only what the clients need to work: the protocol's message formats, the `board:` line, and the word counts and fixed phrases that MacFIBS, FIBS/W and xfibs match (for example `** User name authenticated.`, `You are registered.`, the `toggle` replies and the game messages). Everything else is ParlorNet's own and says so:

- The login banner reads "This is ParlorNet's FIBS-protocol service for vintage Backgammon clients; it is not FIBS. For FIBS, the First Internet Backgammon Server, telnet to fibs.com 4321." FIBS's ASCII-art banner is not reproduced (only FIBS/W's dial-up `MANUAL.SCC` script waits for it; its host scripts wait for `login: `).
- The guest sign-up, `help`, `about` / `version`, the welcome line after login and `whois` are in ParlorNet's words; the message of the day is the parlor's own.
- There are no ratings. The rating field that `who`, `rawwho` and CLIP lines need shows `0.00` for everyone, and `whois` says games are unrated. The "from" field shows `client` for players on this service and `web` for everyone else.
- The extension connects only to the core. It never connects or relays to fibs.com, imports no accounts, and copies no data, help text, news, rules text or bot names from FIBS.

The login line tells the session's style apart:

| Login | Clients | Session |
|---|---|---|
| `connect name password` (one line) | MacFIBS | no `> ` prompts (`toggle telnet` NO); `** User name authenticated.` starts the client's `set` / `toggle` / `rawwho` sequence |
| `name`, then `password: ` | FIBS/W, xfibs, xibc, terminals | a `> ` prompt after every reply and every burst of news (xfibs parses nothing until its input ends in `> `) |
| `login client 1008 name password` | CLIP clients | numbered lines: 1-4 at login, 5/6 for `who` and `rawwho`, 7/8 log in and out, 12-19 chat; no prompts |
| `guest` | any | FIBS-style registration: `name x`, then the server's sign-up steps as prompts (under sign-up password: choose a password, type it again), `You are registered.` |

- Input lines may end in CR, LF or CR LF; output ends in CR LF. No telnet options are sent.
- Sign-in is generic (docs/accounts.md, the dialog): the name alone goes to the server; the FIBS password answers its credential question (the password) and is dropped if none comes; every other step is a prompt with the server's label. As on FIBS, a login only signs in (`USER`): a name with no account is told to log in as `guest`, which signs up (`REG`). Three refused logins close the line.
- Geometry: seat 0 of a backgammon/1 table is FIBS's O (color 1, direction -1, home 0, bar 25) and seat 1 is X (color -1, direction 1, home 25, bar 0), so point numbers are the same both ways. The `board:` line has all 53 fields; positions 0 and 25 carry X's and O's bar checkers. `set boardstyle 3` is the default; 1 and 2 give a small text board.
- Commands: `move 13-9 8-7` (also `m`, bare `13 9 8 7`, `bar-22`, `b 22`, `6-off`; a checker moved through several dice in one pair is split into steps), `roll`, `double`, `accept` / `reject` (a double or a resignation, by state), `resign n|g|b`, `invite name n|unlimited` (no length: resume a running match, else 1 point), `join [name]`, `decline name` (ParlorNet's own addition, since FIBS has none), `leave`, `board`, `pip`, `watch` / `unwatch` / `look`, `who [ready]`, `rawwho`, `whois`, `show games|saved|watchers`, `tell`, `say`, `kibitz`, `whisper`, `shout`, `toggle`, `set`, `away` / `back`, `gag`, `blind`, `help`, `motd`, `bye`. Command words may be abbreviated. Anything else gets a `**` reply, so no client waits.
- Tables: `invite` makes a private table (`NEW backgammon/1 standard match=n vis=private`), sits in seat 0 and invites the other player to seat 1 (`INV`); `join name` sits down at that invitation (`IVL`, `JON`), resumes a running match with name, or joins name's open public table. Invitations made anywhere else, such as the web, telnet or IOS, arrive in FIBS's own two lines, `name wants to play a n point match with you.` and `Type 'join name' to accept.`. `decline name` declines one. The inviter is told when an invitation is declined or expires. `invite name unlimited` is a single money game (match length 9999 on the board line).
- Matches: the plugin plays the games of a match at one table. Between games the extension prints FIBS's `Type 'join' if you want to play the next game ...` and holds that player's output until `join` (the next game has already begun for the server and the web).
- Chat: `say` and `kibitz` are table chat (`CHT`); a table chat event shows as `name says: text`. `tell` goes straight to a FIBS session, or to the table if the name is the opponent. `whisper` reaches the other FIBS watchers of the table and `shout` every FIBS session; neither reaches the web.
- Presence: one shared task polls `LST` and `WHO`. `who`, `rawwho` and CLIP's rows list the players who are online (see "Who is online" in docs/accounts.md). The bot always shows as ready. Players who come online get a `name logs in.` notice (CLIP 7), and players who go idle or leave get `name logs out.` (CLIP 8).
- Left out: ratings and experience (`0.00` and `0` are sent), redoubles, beavers, stored messages, `automove` and `greedy` (accepted as toggles; no effect), the turn clock (FIBS has none; the table's time per turn still applies). A FIBS `leave` only stops following the table: the game goes on and the clock runs.

## DOoM extension (port 6507)

It speaks the commands and wording of DOoM, a MUD for crossword games, so that BobGrid 2.3 and people at a terminal or MUD client can play `gridwords/1`. The sources are DOoM's help files, its English message catalog and BobGrid's class files, read statically. ParlorNet is not DOoM; the banner and `about` say so.

- Connection: plain text, lines end in CR LF out and CR, LF or CR LF in; no telnet options are sent. A new connection is a numbered connector that can read `help`, `about` and `who`. `connect name password` (or `co`) signs in (`USER`); `request name` signs up (`REG`), each further step a prompt with the server's label. Three refused logins close the line. After sign-in come the message of the day between its rules and a sentence on playing the bot.
- World: one room, the Gaming Room, and a board `bd_<table id>` for every open or running Grid Words table (`bd_<player>` and a player's name find their board too). Going to a board (`join bd_12`, `go bd_12`) watches it (`SEE`); `join` there sits down (`JON`); `home` goes back (and stops watching). A player with a running game is taken to its board at sign-in.
- Board display (`b`, `look`, `look bd_12`), as BobGrid reads it: the column guide `   a b c d e f g h i j k l m n o`, a border, fifteen rows with the square of column c at character 2c+1 (a tile in upper case, a blank in lower case, `=` `-` `"` `'` for triple word, double word, triple letter and double letter), a border and the guide. From character 38: the players on rows 2 and 3 (name, the viewer's own rack with `?` for blanks, score, time as MM:SS), `Waiting for <name> to play.` or `The game is over.` on row 5, the bag on row 6, the clock on row 7, `Time penalties are not in effect.` on row 9, and the last play. A placed play shows on the board until it is committed or undone.
- Play: `place` (`p`) takes DOoM's three forms (`8d WORD` across, `d8 WORD` down, `WORD a|d 8d`; lower case in a mixed-case word, `_x`, `-x` or `(x)` is a blank) and checks it with `CHK`, answering with the score; `commit` (`c`) sends `MOV ... PLAY`, `undo` (`u`) drops it. There are also `exchange` (`x`, `?` for a blank), `pass` and `resign`. Refusals use DOoM's sentences where it had one ("Your first play must cross H8.").
- Events: `<name> plays WORD at 8D for N points.`, draws (`<name> draws two tiles from the bag.`, `(You now hold ...)`), exchanges and passes; after each turn `<name> starts the clock.` and `It is <name>'s turn.`; at the end `<name> plays out.`, the rack penalties, `<name> ends the game.` and `> Final scores: ...`. BobGrid sends `b`, `log2 -tagged` and `track -tagged` after the lines that end "starts the clock.", "plays out." and "ends the game.".
- `log2 [-tagged]` writes two 40-character columns, one per player, with the coordinate at 8, the word at 14, the score in [29:33] and the running total in [34:38]; racks are not kept by the core, so the rack field shows dashes, which BobGrid takes for a hidden rack. `track [-tagged]` writes `Unseen tiles: ` and the letters. Both go between `[BEGIN]` and `[END]` when tagged.
- Talking: `"` and `say`, `kibitz` (`k`) at a board are the table's chat (`CHT`); in the Gaming Room they reach the DOoM players there. `'name text` and `page` reach DOoM players only. `beep`, `flip`, `:` and `doing` work among DOoM players.
- Invitations, ParlorNet's own addition: `invite <name>` (at your open board, or on a new one), `accept <name>`, `decline <name>`; invitations from anywhere arrive as one line of text. `who` lists the players online (the core's `WHO`) and the bot.
- Rules: `newboard` makes `classic` tables (six scoreless turns in a row end the game, as on DOoM); boards made elsewhere keep their ruleset. Left out: rooms and objects, the board Workshop (`tws`, `dws`, `certify`: every board has the standard layout), ratings, time penalties, pausing the clock, `extend`, challenges and `withdraw` (words are checked when played; `ospd`, `ods`, `osw` and `sowpods` look words up in the server's word list).

## NetSprocket extension (port 6512)

Hosts NetSprocket games for the Mac: NetBoxes 1.1 (Dots and Boxes). Its protocol was decoded from a game captured between two copies of the program in an emulator and from the program's code. The parts:

- `adapters/nspwire.py`: NetSprocket 1.7's own messages, which every NetSprocket game shares.
- `adapters/nsphost.py`: the shared host. `Join` takes a connection through the join request, the sign-in and the approval, then waits for the program's first message; `GameSession` is what the games' sessions share (the core session, the table's events, the lobby's timeout, the idle note, going away).
- `adapters/netsprocket.py`: the listener and the games it knows. The TCP join request carries no game ID, so the first message after the approval says which program it is (NetBoxes' version request, 0x101), and the core is told the program's name with `CLI PROG`.
- `adapters/nsp_netboxes.py` and `adapters/netboxeswire.py`: NetBoxes' session and its bytes.

The Mac always joins, and the extension is the host. Each connection is a NetSprocket game of its own, with the Mac as the joiner and the extension's player as the host's. Sign-in: the join request's player name goes to the core, and its password answers the credential question (`sign_in_lines`). A refusal is a join denial; NetBoxes never shows one, so for a program with NetBoxes' player type the join is approved, and once its first message shows it is NetBoxes, the reason goes in its chat window before the connection closes.

Silence: neither NetSprocket nor the program sends anything while a player thinks, and a proxy on the way may reset a connection that carries nothing for about 150 seconds. So after 45 seconds with no message either way (`netsprocket.idle_note_secs`), and every 75 seconds after that (`netsprocket.idle_repeat_secs`), a chat line goes to the Mac: in a game, whose move it is and the time left, otherwise what to do next.

NetBoxes 1.1:

- Commands: the shared set in the chat window. `/open` and `/invite` take a size (`7x4`) and `/open` 3 or 4 players; tables made here are `NEW dotsandboxes/1 standard size=WxH players=n`. A Mac sits down at any standard table, of any size and two to four players; majority tables are refused, since NetBoxes plays every game until the board is full. A game starts when every seat is taken.
- Slots: NetBoxes gives turns in slot order. The version answer gives the Mac slot 0 (and says joiners may not start or stop games, which turns those menu items off); at the start the other seats take slots 1 to 3 in the table's order from the Mac's seat, each as its own NetSprocket player with its own face. The start names the first player's index.
- First move: a copy of NetBoxes that is sent a start never takes the first turn itself. When the core gives the Mac the first turn, the start names the player before it, who passes at once in that Mac's game only.
- Moves: the Mac's dot and direction become `MOV table line`. Another seat's `LINE` event goes to the Mac as a dot and a direction from that seat's player, with a pass when it closed no box. A `GONE` seat gets a step out, so the Mac skips it. A line the core refuses means the games differ: the Mac's game is aborted and resigned.
- The end: every copy of NetBoxes ends the game when the board is full, as the core does. The chat gives the core's result and box counts; NetBoxes' own points (lines, boxes and time penalties) are its display only. A game the core ends early is aborted on the Mac. The next game in the same session is preceded by an abort, since a start into a finished game's window leaves it blank.
- Left out: mines, random lines, NetBoxes' points as the score, the Mac's own Start Game, the majority ruleset.

## NetLuff extension (port 6517)

It is the other copy of NetLuff 1.4 for Macs that connect to the parlor. NetLuff has no port setting and always connects to TCP port 1744, so the extension listens on 6517, the host publishes it as 1744 as well (deploy/install.sh), and it declares 1744 (`catalog.PUBLISHED`). The protocol was read from the program's PowerPC code and from games between two copies and against a scripted peer in an emulator; the module's docstring has the messages.

- Sign-in: NetLuff sends its player's name but nothing secret, so the name alone never signs in. `/signin PASSWORD` in the chat box signs in the name from NetLuff's name box, and `/signin NAME PASSWORD` another; the name goes to the core and the password answers its credential question (`sign_in_lines`). Under the sign-in method `none`, `/signin` alone signs in NetLuff's name.
- On connecting the extension answers NetLuff's `ip`, `sa` and `nm` with its own, and `sa0` takes the move away from the Mac until a game starts. Its own lines in the chat box start with `*** `, as NetLuff's notes do.
- Commands: the shared set (chat-commands.md) through `adapters/chatcmd.py`. Tables made here are `NEW fiveinarow/1 freestyle size=20` (NetLuff's 20 by 20 board, and five or more wins, as in the program). An open table's options are not in its view, so the extension keeps a mark with each table it makes (`TDS table netluff 20 freestyle`) and seats a Mac only at a table with that mark. Invitations from anywhere come in the chat box with NetLuff's page sound (`pe`).
- The game: the core decides who moves first; when the game starts the Mac gets the opponent's name for its window title and `sa1` if it is seat 0. Moves go both ways as NetLuff's four digits. NetLuff checks only its own player's lines: when the opponent makes five, the extension sends the move, a line in the chat and `wn` with the first five points of the core's winning line, and the Mac shows "Loser!" and hangs up. When the Mac's player makes five, NetLuff sends the move and `wn` and hangs up, and the core ends the game on the move. A resignation, the turn clock or a full board ends the game in the chat. NetLuff clears its board only when it connects, so a connection plays one game, and a Mac that goes away during its game resigns it.
- A move the core does not take cannot be taken back on the Mac: the player is told, and the game goes on on the web or by telnet.
- Silence: after 45 seconds with nothing either way (`--idle-ping`) the extension sends `pn`, which NetLuff answers with `pr` by itself, so a proxy that resets silent connections sees data both ways.
- Left out: the Mac's page button, watching, resuming, other board sizes and the `standard` ruleset.

## Networdz extension (port 6516)

The parlor is the host of Networdz 2.0. Networdz has no server: one player's copy hosts, deals, judges the words and connects out to each remote player's copy, which waits in Answer mode. Here each connection is one Networdz player, a guest seated at an ordinary Grid Words table beside players on any other frontend and the bot, and the extension speaks the host's side of Networdz's protocol to it. The table deals, judges every word with its own list and ends the game. The stock program only answers, so it reaches the parlor once a patch makes it connect out, which is a later step; the extension only listens. The protocol was read from games captured between copies of the program and checked against the stock program in Answer mode; the module's docstring maps each message and what the program was seen to need.

- Connecting: on each connection the extension sends `X` (the guest is seat 1 until a game) and a players' list (`F`) with the parlor as seat 0, named ParlorNet, so the parlor's lines in Networdz's chat come under that name. The guest answers `D` with its name.
- Sign-in: Networdz sends names but nothing secret, so `/signin NAME PASSWORD` (or `/signin PASSWORD` for the name in `D`) in its Chat window signs in (`sign_in_lines`).
- Commands: the shared set (chat-commands.md) through `adapters/chatcmd.py`; `/open N` opens a table for N players. Each table where the guest sits is marked with `INT table false a Networdz program receives the bag and all racks` (docs/protocol.md, Tables marked integrity=false).
- The game: at the table's `START` the extension reads every rack and the bag (`VUE table O`) and sends `X` with the guest's seat, the rules (`E`, every extra rule off), the players (`F`: the bot as a Computer, other Networdz players as Remote, everyone else as a Person, and a seat of type none named ParlorNet for the parlor's lines when one is free), the bag (`A`), the order (`R`) and each seat's first draw. Another seat's draw is `P` and `Q` with the places of the tiles the table dealt it. For the guest's draw `A` holds only those tiles, so the program's random pick takes them, and then the whole bag again. The guest's play (`J`) is `PLAY`; `M` 0 when the table takes it, else `M` 7 with the word the list lacks (at most five letters, and the seven bytes a stock host ends `M` with) or the code of Networdz's own message for the reason (tiles not in a line, not connected, missing the center, no tile), then `I` to the same seat, with the table's reason in the chat. A pass is `K`; while the bag holds 7 tiles the extension asks for the discards (`N`) and an `O` with tiles is `EXCH`. Another seat's play, exchange and pass go to Networdz as a host sends them (`J` and `M`; `K`, `O`, `P`, `Q` and `A`), each turn as `I`, the end as `S` (or `Y` after a resignation, a clock run out or the operator's end, with a line saying so). Chat goes both ways.
- Each guest's game keeps its own numbering of the 100 tiles (`Tiles`); the board, each rack and the bag are kept in step with the table's events, and when they no longer agree the extension stops Networdz's game (`Y`) and says to finish on the web or by telnet.
- Left out: Trade Blanks, Exchange 4 of a kind, Timed and Tournament Rules, other configurations and languages, saved games, watching, and a game that began before the connection (Networdz has no message that sets up a board).

## Awale extension (port 6515)

It is a small IRC server with what Awale 2.x uses (registration, `LIST`, `JOIN` with a key, `MODE`, `TOPIC`, `PRIVMSG`, `PING`), and the channel is the session's own. Its other members are the parlor's players, each with an Awale nick (`awpl` and four hex digits) and Awale's introduction line: ParlorNet (the server, which talks in private lines and refuses a challenge), the bot and the players online from `WHO`. The protocol was read from a captured session and the program's PowerPC code; the module's docstring has the mapping.

- Sign-in: Awale sends no password, and the program refuses chat lines that begin with `/`. So `!signin NAME PASSWORD` in Write to group signs in (`sign_in_lines`), and the shared chat commands are typed with `!`. Under sign-in `none`, the name in the program's introduction signs in.
- Challenges: the Mac's challenge (code 2) is `/invite` on an Oware table (`NEW mancala/1 oware`, the Mac in seat 0); the member accepts (code 3) when the game starts and refuses (code 4) when the invitation ends. An invitation to the Mac from anywhere is a challenge from the inviter's member: Accept is `JON`, Decline is `UNV`. Invitations to tables with store rules are named in the chat only.
- Who moves first: the member answers the Mac's choice number (code 9) with one just below or just above it, so that seat 0 moves first.
- Moves: the Mac's code 6 (field 2, the hole from 0) is `MOV table hole+1`; the opponent's `SOW` goes to the Mac as code 6 with the board field Awale writes (move count, who started, the twelve holes, both captures, the hole).
- The end: when the core ends a game that Awale would play on (more than 24 seeds, a repeated position), the member ends it as a deadlock (code 10, reason 3). When the player to move cannot feed the other, Awale's rule has that player move once more and then ends the game by itself with the same totals: if it is the member, it makes that move. A resignation or a timeout is the member abandoning (code 10, reason 1), or the Mac's own timeout reason 2. The Mac's Cancel game (code 10, reason 1) is `RES`.
- Keeping the line alive: an IRC `PING` every 60 seconds, which the program answers.
- Left out: ratings (every member shows 100 points), watching, Awale's other rules, the result mail (switched off in `internet.cfg`), resuming a game (Awale cannot); a game left when the Mac goes away stays at the parlor.

## batnav extension (port 6514)

It plays the part of `btserver`, the server of Batalla Naval (batnav), for its clients of 0.50 and 0.60: the X client (XView, and GTK in 0.60), the ncurses client and the Windows 3.x client. The protocol was read from the source and checked against the original server and the built clients; the module's docstring maps each record.

- Records: fixed 108-byte records both ways, read buffered and sent whole. Every client is player 1 to itself, and the other seats of its table follow in seat order.
- Sign-in: BNJUG carries a name of up to 16 characters and nothing else, so the name is only the client's claim. On a parlor that signs in by name alone it signs in (`HELO`); elsewhere the greeting asks for `/signin NAME PASSWORD` as a message, which goes through `sign_in_lines` like NetLuff's chat. A backslash works in place of the slash, and the ncurses client's player is shown the commands that way, because its message field takes the slash key as a backspace.
- Commands: the shared set (chat-commands.md) through `adapters/chatcmd.py`, with `/quit` of its own. Tables made here are `NEW navalcombat/1 batnav`; a batnav client sits down at any batnav-rules table, wherever it was made, and at no other. Invitations to the player arrive as lines in the message window, every three seconds.
- The game: BNWRI's board is checked by batnav's rules (fleet_of) and answered as `btserver` did. Once the table's game has begun, the fleet is placed there ship by ship, largest first, and made ready. When every seat is ready (the READY events), the client gets BNSTR with the players' names, then BNTRN on its turn and BNWHO on the others'. BNHIT is the shot (`MOV`); a refused shot is told in a line and BNTRN gives the turn back. Shots at the client's fleet go to it as BNHIT, a sunk ship square by square, and BNREA answers from the client's view of the table, with the ships of every other seat hidden whatever the client asks.
- The end: the loser gets BNLOS, then `The Game is over: Player n is the winner.`; the winner gets `Player n is dead.` (or `Player n quits the game.` after a resignation), then BNWIN, as `btserver` sent them. The client then sends a board for its next game.
- BNSTR from the client (its Start button) gets BNSOL and a line saying what the game waits for. BNEXT, or a lost connection, resigns a running game, since a batnav client cannot come back to one; before the start it leaves the table.
- Left out: games of three to five players (Naval Combat tables seat two), the supervisor view (BNSUP), player numbers as `btserver` gave them, and watching.

## ICDS extension (port 6518)

It speaks what xcheckers 2.2.3 reads of the Internet Checkers and Draughts Server, a FICS-derived server whose source is lost, so the extension follows what the client's source shows. xcheckers runs `telnet` to the server: the player logs in and types commands in the terminal, and the program itself reads only boards and five refusals and sends only moves, `set style 5` and `refresh`.

- Connection: plain text, CR LF out, CR, LF or CR LF in; no telnet options are sent. As on FICS, a reply follows the `icds% ` prompt on its line (so a refusal reads `icds% Illegal move.`, which xcheckers answers with `refresh`), and anything else starts on a new line. No line but a board starts with `Game`, `<5>` or `icds%`, and none looks like a simplech board.
- Login, the FIBS way: `login:` takes a name and `password:` its password, which answers the credential question (`USER`); `guest` signs up (`REG`), with the server's steps as prompts. A name with no account is told to log in as guest. Three refused logins close the line. A second login with the same name ends the first connection.
- Boards: style 1 (text, from the player's side, starting `Game n (black vs. white)`) until the player or xcheckers sends `set style 5`; the choice is kept with the player (`PRF style`). Style 5 is one line: the game number, `e` for English checkers, the viewer's side, the side to move, both names, the 64 cells from Black's back row and two clocks. A clock shows the time left on the turn, or the whole time per turn for the side not to move, at most 599 seconds, since xcheckers keeps each clock in 8 bytes. A board goes out when a game starts, when the turn passes and at the end.
- Moves: `11-15`, `15x22`, `15-22-29`. A move given as its two end squares, as xcheckers sends a drag, is the legal step between them if there is one (from the view's `M` lines); else the lines of jumps that join them are found on the board by their shape and checked with `CHK`: one is played, two or more are refused with `Ambigous move.`, spelled as xcheckers matches it. A jump at a time works too: after a jump that must go on, the board comes again with the same side to move. When a turn's steps are complete the extension sends `END`. A move out of turn is `It is not your move.`, a refused one `Illegal move.` with the plugin's reason.
- Commands, in FICS's manner: `match NAME [minutes] [black|white]` (NAME's challenge taken up, NAME's open table joined, or a new public table with NAME invited to the other seat; `match bot` plays the bot; minutes set the time per turn), `accept` and `decline` (a challenge, or a draw offer waiting for an answer), `draw` (offers one, or accepts the other player's), `resign`, `refresh`, `set style 1|5`, `games`, `observe N`, `unobserve`, `who`, `finger`, `tell`, `say`, `kibitz`, `shout`, `motd`, `help`, `quit`. Lines starting with `/` are the shared chat commands (adapters/chatcmd.py), so `/open`, `/join`, `/list` and `/note` work as elsewhere. Challenges from anywhere arrive as `Challenge:` lines, a match's start is followed by what the opponent plays with (`ann plays with Xcheckers 2.1 on a SPARCstation 2.`, from the `CLIENT` event after their `JOIN`), the opponent's turn as `bot moves 22x15.`, and the end as FICS wrote it, `{Game 3 (amy vs. bot) bot wins: amy has no pieces left} 0-1`.
- Left out: ratings, game clocks (the table's time per turn applies), the other draughts variants xcheckers knows (international, Italian, Russian), examining and stored games.

## Worthy Opponent extension (port 6519)

It is the answering copy of Worthy Opponent 2.0, Future Ideas Today's pack of modem games for DOS (1988-90). The player dials the parlor from the program's phone book with `ATDT host:6519` (a number that starts with `AT` goes to the modem as it stands), through a WiFi modem or an emulator's modem, and the program speaks its link protocol on the byte stream after CONNECT. The protocol was taken from games between two copies in DOSBox through a logging relay, and the generator behind the seed from the program's code; the module's docstring has the frames.

- The wire: nine-byte frames (two data bytes sent twice, a sequence number and a sum), each answered with 06 and sent again without it. Talk is typed keys, a game is its keys and turn events (81 end, 82 start), and each copy plays both sides from them and a shared seed, so no move crosses the wire as such. The extension keeps both sides' boards and cursors as the program does and turns keys between the two players' boards where the program turns them (Checkers).
- Sign-in: the handshake carries the player's name and nothing secret. The extension opens the Talk window from its side (the F6 line lights up), and `/signin PASSWORD` or `/signin NAME PASSWORD` there signs in (`sign_in_lines`); under sign-in `none`, `/signin` alone.
- The games: the player picks CornerStone, Checkers or Quinte with F8 and the extension enters it at once, which brings the seed: Turbo Pascal's `Random(100)` on it gives the dialing player the first move above 50. Tables made here (`/invite`, `/open`) put the player in that seat: `NEW reversi/1 standard`, `NEW checkers/1 american limit=0`, `NEW fiveinarow/1 freestyle size=19`, each marked `TDS table worthy <game>`. `/join` and `/accept` take a seat only when it is that one; otherwise the seat waits for a new draw, which the player makes by leaving the game (F10) and picking it again.
- Moves: a PC move goes to the core when its Space completes it (Checkers as its steps and `END`); the opponent's move goes to the PC as the keys that make it, ending with 81 unless it ends the game. A CornerStone pass is 82 and 81 both ways.
- The end: the program sees a game end on its board. A resignation, the core's turn clock or a draw is said in Talk, and the extension leaves the game (`XG`). The PC's `XG` during a game, its 87 (its own clock ran out) and hanging up resign the game.
- A telnet line: some WiFi modems treat the line as telnet. The PC's first frame always carries FF, which such a modem sends doubled, so the extension reads FF FF as FF and doubles its own FF from then on, answers telnet negotiation (binary and suppress-go-ahead yes, the rest no) and reads CR NUL as CR until binary is agreed. Its Talk text and names are split into frames that hold no FF and no CR NUL.
- Left out: Backgammon (the program makes its dice from the seed by its own procedure, and the core rolls its own) and the other eight games, watching and resuming.

## RSCARDS extension (port 6520)

It plays the part of GEnie's lost host program for the RSCARDS graphics front ends (Mac, IBM PC, Commodore 128, Amiga), with screens of its own for all ten games. The packets are in `adapters/rscwire.py`, the line, the scenes and the session in `adapters/rscards.py`, and the lobby and the games' screens in `adapters/rscgames.py`; the module docstrings describe the packets, the front ends' limits as found and the screens.

- The line: the front ends speak only over a serial port, so players come through a WiFi modem or a serial bridge. Telnet options from a modem in telnet mode are refused; the extension sends none. A connection starts in terminal mode with a one-line welcome and the auto-shift (`ENQ ENQ ENQ 1`, `FLC n 9`, `LAUNCH 1 n`); the front end's identification line starts graphics mode whenever it comes (the IBM PC version, which has no terminal, sends it once it is started, often minutes after the dial). The identification gives the machine (and so a color or a mono screen) and the version, which the extension says to the core (`CoreClient.claim`). With no `FLC` after `--guide` seconds (12), whoever is there gets a 40-column guide: run the RSCARDS program now, or press T (or RETURN twice) for the text games, which the telnet extension's session (`adapters/telnet.py`, `main_session`) then plays on the same connection, in this process; a line that does not speak telnet gets none of telnet's codes (`PlainWriter`). The trigger comes again every 15 seconds while it waits (for a front end loaded after a terminal program dialed), and the guide once more after two minutes.
- Click codes leave out `+`: a click sends its code three times, and `+++` after a quiet second is a Hayes modem's escape, which puts the modem in command mode and kills the line.
- Packets: up to `--window` bytes (64; the IBM front end loses input when much more waits) go out ahead of their acknowledgments; a NAK, or nothing acknowledged for 15 seconds, sends again everything not yet acknowledged, and a NAK with nothing waiting draws the whole screen again. Two identical packets never go in a row (the front end would take the second for a repeat): a packet that does nothing goes between them.
- Screens are scenes: a base drawn when the screen changes, and items, each with the packets that draw it and erase it, of which only the changed ones are sent; fills that join up go as one. Shapes are stored in the front end as macros once a session and played where needed: rows of squares, the points of a Backgammon board, grid lines, a Grid Words board's premium rows, and the pieces (checkers, discs, stones, Mancala's seeds, a hit or a miss at sea, the ring that marks where a picked Backgammon checker can land), so a piece costs 8 bytes. Click areas go out after the drawing, when nothing else waits. The Mac front end holds 30 click areas of each kind and the IBM front end 40, so no screen defines more than 30: a board is a grid of B areas for its columns and H areas for its rows, and one click reports both (`Session.pair`). The frame an H area shows under the pointer lies on pixels a move never draws again (grid lines, gaps between rows), so it leaves no stray line.
- Sign-in: two input fields, the name and then each answer the server asks for (`sign_in_lines` with prompts), a secret answer typed into a field drawn in one color. Under sign-in `password` the name alone never signs in; a new name is offered a sign-up.
- The lobby and the games: Bot makes a private table with the bot (`NEW`, `JON`, `INV`), Open a public table; the lists poll `LST mine`, `LST open`, `LST playing` (the core's capped lists: the lobby shows the first few, open tables to join and at least one game to watch), `IVL` and `WHO`, and a screen looks its table up with `LST table=id`. Watch shows a game's screen to a watcher, who `SEE`s the table and `LVE`s it when leaving. A refusal, such as the core's `ERR LIMIT` for a player at the most games or waiting tables allowed, is shown in the message area, and a table the player could not sit down at is left (`LVE`). A game's screen polls `SIN`, and fetches the view (`VUE`) when something happened. The entry line takes chat (`CHT`) and the shared chat commands through `adapters/chatcmd.py`; a typed move is played as a click would be.
- Left out: GEnie's own games and its Waiting Room.

## The extension channel

Every server extension reaches the core on its extension channel (127.0.0.1:6590 in the container): TLS 1.3 with its own pre-shared key, `--core 127.0.0.1:6590 --key /data/frontends/NAME.key` (the container's start script enrolls each extension it starts). A server extension never checks or keeps a credential: it signs in with the name alone, relays the player's answers to the server's steps (a password the client supplied answers only a question flagged `cred`), and sends `OUT` when the player leaves (telnet, IOS, FIBS, Outland, DOoM, GameMaster, NetLuff, Networdz, NetSprocket, Awale, batnav, ICDS and RSCARDS hold one connection per player). It opens that connection only once its client has sent a login line, passes the client's address with `SRC` (for the core's per-address limits), and counts its clients that have not signed in yet, per extension and per address, with a short time to log in (`Gate` in `adapters/common.py`), so idle connects cannot use up its share of the extension channel. The container runs everything as one unprivileged user by default; docs/security-design.md (Containment) has the opt-in separations. New server extensions follow the same rules (docs/security-design.md, what each server extension must do).

A server extension may keep a little data with each player, under its own key name, with `PRF GET`, `SET`, `DEL` and `LST` (docs/protocol.md, data kept per extension and player): at most 16 keys of up to 12 characters, values of up to 56 printable ASCII characters, 1024 bytes per player. It reads and writes only its own namespace and only for the player signed in on the connection. `CoreClient` has `prefs()`, `pref_get()`, `pref_set()` and `pref_del()`, and for settings `load_pref(key, choices, default)` (at sign-in; never fails a sign-in) and `save_pref(key, value)` (when the player changes it). The first user is the telnet extension's movement keys (`MOVE_KEYS_PREF`, `MOVE_KEYS` in adapters/common.py); the side of the Backgammon home board (`BG_HOME_PREF`, `BG_HOMES`: `bghome`, `right` or `left`, missing meaning right) is kept by the telnet and web extensions, and Play shares the web's. Nothing secret goes there.

## Rules of the seams

- Server extensions and bridges are the only components that know a foreign protocol; neither the core nor a game plugin does.
- A server extension can only do what a client could do; its trusted credential asserts identity but grants no extra power over games.
