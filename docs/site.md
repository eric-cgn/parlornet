# The web sites

ParlorNet has two web sites in one style.

- **The game server's site**, served by the web extension (`adapters/web.py`) on port 6500 of each ParlorNet server: the welcome page with the message of the day, sign-in and sign-up and the ways to play from each kind of computer, the lobby and tables, and the games this server hosts. It has no list of protocols or ports: technical readers find them on the docs site. Its pages are the server's own, and change with its configuration.
- **The docs site**, http://docs.parlornet.org/: a static site built from the repository by `tools/build_docs.py` (`docsite/`) and published to GitHub Pages by `.github/workflows/docs.yml` on every push to main. It holds what is the same for every ParlorNet server: the clients for each game and each kind of computer, their setup, the protocols reference and the docs. The game server's pages link to it at the setting `site.docs_url`. The site is served over plain HTTP as well as HTTPS, with HTTPS not enforced, so period browsers, which cannot use today's HTTPS, can read it. Its address is written with `http://` everywhere for the same reason.

Both are HTML 3.2 for any browser with tables, forms and image maps, back to Mac Mosaic 2.0 and Netscape 1.1, at 2400 to 14,400 bit/s. ParlorNet recreates period game-server protocols so the original game programs, its native clients, first released between 1977 and 2000, can play, and both sites lead with them; the web pages are the fallback. This page maps both sites and gives their page frame and the rules the pages keep. Each fact lives on one page, and the others link to it.

### ParlorNet Play (`/play/`)

The modern client (docs/modern-client.md) is a site of its own, served by the Play extension (`adapters/playserver.py`) on port 6513, usually behind a reverse proxy at `https://` the parlor's name `/play/`. It is not bound by these pages' rules: it is HTML5 with CSS and scripts, for today's browsers. On the web extension, `/play` and everything under it answer with a 301 to `play.public_url` when that is set; otherwise with a short page linking to the Play extension's port while it runs, or a 404 saying Play is not offered here. The welcome page's Any new computer links to it only while it runs.

| Address | What it is |
|---|---|
| `/play/` | The app: `index.html`, `play.css`, `net.js`, `gfx.js`, `app.js`, `game-<type>.js`, the service worker `sw.js`, `manifest.webmanifest`, `notifications.html` and the icons, from `adapters/play/`, as they are (`index.html` gets the classic pages' full address). `/play` and `/` redirect here. They are sent with a Content-Security-Policy that allows only this site's own files and its WebSocket. |
| `/play/ws` | The WebSocket that carries PARLORNET/1 (docs/protocol.md, WebSocket). |
| `/play/session` | POST: `h=` the one-time handle a sign-in over the WebSocket gave sets Play's own session cookie (`pnplay`, `Path=/play/`); `out=1` clears it. The HTML pages' cookie (`pn`) is separate. |
| `/play/palette.json` | The Grid Words presets and what the client draws them with (adapters/palette.py). |
| `/play/push` | POST: a browser's push subscription, from Play's own pages with its session cookie, for notifications (docs/play-notifications.md). |

### Pictures

The welcome page shows a picture of each kind of computer beside its row, and the Games page, each game's page and the lobby's Start a table show an icon for each game. They are GIFs in `adapters/img/`, which the web extension reads when it starts and serves like its other images (`adapters/siteimages.py`): `machines/<anchor>.gif` at `/img/m/<anchor>.gif`, at most 56 by 44 pixels, and `games/<type>.gif` at `/img/g/<type>.gif`, 32 pixels square. Each has a transparent background, whose color is white for a browser that does not show transparency, and is under 2 KB. Each `<img>` has its size and ALT text: what the photo shows (a Commodore 64, a DEC VT100 terminal), or what the icon shows (Black and white discs, Letter tiles).

The computers' pictures are photos from Wikimedia Commons, each in the public domain or under CC0, CC BY or CC BY-SA. Each was cropped, cut out from its background, scaled down and reduced to 16 colors or fewer, which a 256-color screen dithers like any other photo. `adapters/img/CREDITS.tsv` records each one: the picture, what it shows, its file page on Commons, its author, its license and the license's address, and what was changed. The credits page (`/credits.htm`) is built from it, and a test fails when a photo has no row there, or a row has no photo or a license outside those. The game icons and the picture for Any new computer, a laptop and a phone, are ParlorNet's own, drawn in web-safe colors by `tools/site_icons.py`, which writes them into `adapters/img/`; a test checks that the files are what it draws.

The documentation's old addresses on this site answer with a 301 to the same page on the docs site, the body a plain HTML 3.2 page with the link: `/frontends.htm` (to `index.html`, keeping `?plat=` and `?arch=`, which the docs site's finder reads), `/browsers.htm`, `/telnet.htm`, `/setup/<id>.htm`, `/eclipse-68k-fix.htm`, `/docs/index.htm` (to `docs.html`), `/docs/<name>.htm` (to `docs/<name>.html`), `/protocols.htm` (to `protocols.html`, the protocols reference), and the Eclipse 68k Fix's downloads and screenshot (`/download/...`, `/img/eclipse-68k-fix.gif`). When the operator clears `site.docs_url`, they answer Not found, and no page links the docs.

`site.docs_url` is a server setting, like `site.contribute_url`: the admin menus (Server, Docs) or the settings file, else `PARLOR_DOCS_URL`, else http://docs.parlornet.org/; set to nothing, it is cleared. The core hands it to the web extension on the `DOC` line of `PRL`.

The downloads of Eclipse 68k Fix and Install ParlorNet Rulebooks, with their READMEs, are the only files the docs site carries besides its own pages and images. They are not built here. Each is built and released in its own repository: Eclipse 68k Fix in [eric-cgn/parlornet-eclipse-fix](https://github.com/eric-cgn/parlornet-eclipse-fix), and the ParlorNet rulebook, the game rulebooks and their installer in [eric-cgn/parlornet-gamemaster](https://github.com/eric-cgn/parlornet-gamemaster). `docsite/downloads.json` pins each file the site serves: the repository, the tag, the file and its SHA-256. Install ParlorNet Rulebooks comes from its release as `.hqx`, `.bin` and `.dsk`, the release's only files, so the rulebooks' READMEs come from the repository's source at the same tag, and their entries also give their path there. The docs workflow runs `tools/fetch_downloads.py` first, which fetches each file from its GitHub Release or its repository and checks its SHA-256, and then builds the site with `--require-downloads`, so a release that is not published, or a file that differs from the one pinned, stops the build with a message naming it. The site serves the files at `download/<file>` over plain HTTP, which period browsers can fetch where GitHub's HTTPS addresses are out of their reach. Each page lists the files with their sizes and MD5s. A local build of the site without them leaves them out, and the pages say so and link the READMEs in their repositories. A new release of either program reaches the site when its tag and SHA-256s are recorded in `docsite/downloads.json`.

**Who owns what on a client's page.** `adapters/clients.py` holds what the tables, the summary grid, the finder and the tests need, and the download links: the name, kind, year and its one-line note, the OS text, platforms and processors, version, status, its ratings, games, port, protocol, the sources to get it from, and the groups still running (`COMMUNITIES`, with the date they were last checked). `docs/clients/<id>.md` holds everything a person reads as prose, under a fixed outline: History, Getting it, Setting it up, Known quirks, Screenshots. `docsite/clientpages.py` joins the two. A test fails when a client has no page, a page has no client, a page leaves the outline, or a screenshot is missing, not a GIF, wider than 320 pixels, too large or without a caption, and when a client's ratings lack an explanation, a medal lacks its date or a Silver its patch's link, or an unsupported program its reason. The rating icons are ParlorNet's own 16-pixel GIFs with a transparent background, drawn by `adapters/medals.py` (`tools/medal_icons.py` writes them into `static/img/`); each `<img>` has its size and its word as the ALT text, so a text browser reads "Gold" and color is never the only sign (each medal also carries its initial). [docs/clients/README.md](clients/README.md) tells contributors how to add a client, a quirk, a screenshot or a group.

The docs site names no server: setup steps say *host* for the name of the server you play on, the ports are the usual ones, and the sign-in steps are given for every method a server may run. Only `docs/` is read for doc pages, and `docs/clients/` becomes the client pages instead. Outside `docs/`, the build reads only the README's "Run your own parlor" section and `deploy/README.md`, for Run a server.

**Diagrams.** A doc can show a diagram as a picture on a line of its own, `![Caption](../static/img/diagram-name.gif)`, which GitHub shows as it is and the docs site shows with its size, the caption as its ALT text and the caption under it, as a client's screenshot is shown. Each diagram's source is an SVG in `docs/diagrams/`, edited as text. `python3 tools/diagrams.py` renders each one with rsvg-convert and maps it with ImageMagick, without dithering, to 16 web-safe colors, writing `static/img/diagram-<name>.gif`; both files are committed, so building the site needs neither program. A GIF is what every browser the site serves can show, back to Mosaic and Netscape 1.1, and none of the period ones shows an SVG. A diagram is at most 480 pixels wide, to fit a period screen, and at most 21 KB, in black text on white, ivory or light felt. The diagrams are:

| Diagram | Shown in | What it shows |
|---|---|---|
| `parlor` | README.md, deploy/README.md (and so Run a server), architecture.md | the players' programs, the reverse proxy for ParlorNet Play, and the processes in the container with their ports |
| `request-path` | architecture.md | a move's path from the player's program through a server extension to the core and the game's plugin |

`python3 tools/build_docs.py` builds the site and writes it into `build/docs-site` (git-ignored); `--out DIR` writes elsewhere, into an empty folder or one the tool wrote before (it empties it first). Every link is relative, so the folder opens from disk or any address.

On `index.html` and `docs.html`, a script writes a Find box (and, on Clients, Platform and Processor menus) and hides the rows, and the lists or tables left empty, that do not match, with a count. It writes the box only where the browser has the DOM it needs (`getElementsByTagName`); anywhere else there is no box and every row shows. The page's content is the same with or without it. The Clients page's script reads `?plat=`, `?arch=` and `?q=` from its address, which is how the summary grid's links and the game server's old `/frontends.htm?plat=...` land on a narrowed list; without the script they land on the full one.

## The page frame

`adapters/webstyle.py` holds the frame, the palette, the faces and the helpers every page of both sites is built from (`frame`, `h1`, `h2`, `p`, `callout`, `data_table`). A page is:

1. The masthead, a felt-green column with the emblem beside an ivory plate with the name ParlorNet and the tagline, "Turn-based game server for any computer, old or new", and the navigation bar under the plate. On the game server's site the bar holds exactly Welcome, Lobby, Games and Docs (the docs site, left out when `site.docs_url` is cleared), and, while a player is signed in, Sign out last, which ends this session and shows Welcome. Sign-in and sign-up are on the welcome page; the lobby shows the sign-in page to a browser that is not signed in. A public page (Welcome, Games, a game, the leaderboard) knows a signed-in player by a session that resumed here lately, without asking the core, and then shows the signed-in bar. On the docs site it holds Clients, Protocols, Browsers, Telnet programs, Docs, Run a server and Source (the project's home). The page being shown is in bold instead of a link.
2. The page's own content, its heading (H1) first and then its sections (H2).
3. The footer. On the game server's site it holds the server's name from the core's greeting, and a link to the message of the day when there is one; on the docs site, "These pages cover every ParlorNet server.", a link to the source code at the project's home, and "ParlorNet is free software."

The lobby, a table, the activity, the profile pages and the resign question use the compact frame: one bar with the name and the same navigation with Sign out. The account pages (your profile, your preferred machine, Grid Words colors, Backgammon board, changing your password, signing out everywhere) are under Your account in the lobby, and Activity and the leaderboard are linked at the top of the lobby. The bar's Lobby and Sign out go through `link()`, so they carry the action check (`x=`) and, for a browser without cookies, the session (`s=`). A link to a profile carries only the session (`link.plain`), since it changes nothing and a lobby has many of them. A game's board markup comes from its module in `adapters/games/` and goes into the table page as it is.

The body of a redirect (301, 302) has no frame: browsers follow the redirect without showing it, and a move would otherwise cost the frame's bytes on every click.

## Faces

Text is in `Geneva,Helvetica,Arial`, the Mac's screen face followed by the Unix and Windows stand-ins. Headings and the name are in `Chicago,Charcoal,Arial Black`, the Mac's system face (Charcoal from Mac OS 8) followed by the Windows stand-in. Code stays in `TT`, the browser's own fixed face.

FONT does not carry into table cells in Netscape, so every cell has its own. The docs are set as a manual: their body text and tables are in the browser's own text face (Times, mostly), and only their headings take the site's face. With the frame and headings a long doc grows by under a tenth; a FONT per paragraph and per cell would add a third.

## How each class of browser shows it

- Netscape 3 and later and Internet Explorer 3 and later show everything, faces and cell colors included.
- Netscape 2 and Internet Explorer 2 show page and font colors but no cell colors. So no text sits in a dark cell and no text has a light font color; where a cell's color is missing, the text is still dark on white.
- Mill (68000 Macs, 1-bit screens) turns text on a dark background white. The felt column holds only the emblem, and the light felt and ivory cells keep their black text.
- Lynx, Mosaic and MacWeb show no color at all, only black on white. Their tables have no borders, so each table also has a bold header row, and no fact is told by color alone.

As plain text (Lynx), every page reads in order: the name and tagline, the navigation, the page's heading, its sections, the footer.

## Rules the pages keep

Tests check each of these on every page: `tests/test_site.py` on the game server's site, `tests/test_docs_site.py` on the docs site.

- HTML 3.2 elements and attributes only, plus BGCOLOR on table rows and cells and FONT FACE and COLOR. No CSS, no `style=`, `class=` or `id=`. The only scripts are the table page's optional refresh and the docs site's finders; every page works without them.
- Decimal character references only (`&#39;`), besides `&amp;`, `&lt;`, `&gt;`, `&quot;` and `&nbsp;`. ASCII only.
- The message of the day goes in `<pre>` as the core sends it (each line at most 73 characters, so the operator's ASCII layout reads as on telnet), every character escaped, its `http` and `https` addresses made links. The welcome page has no welcome prose of its own.
- Sign in never turns into a sign-up: the sign-in form only signs in, and New account has its own page and form.
- The content never sits inside one big table: Netscape shows a table only once all of it has arrived.
- The frame has one image, the emblem; the compact frame has none. The welcome page adds the rating marks (served here, drawn by `adapters/medals.py`), each with its size and its word as the ALT text, and a picture of each machine; the Games page, each game's page and the lobby add the games' icons (Pictures, above). A table page has the game's board image (one per board, kept by the browser).
- Every action link and form goes through `link()` and `hidden_fields()`; sign-in answers go by POST and never into an address.
- Byte budgets on the game server's site: the welcome page 16 KB (the forms and the guide by machine, with each machine's picture), the games page 9 KB, a game's page 8 KB, the picture credits 6 KB, the sign-in and new-account pages, their steps and notices 3 KB, the lobby 12 KB plus 600 bytes a table, a table page 3 KB besides the game's own parts, the Activity page 9 KB, a profile 6 KB. On the docs site: Clients 60 KB (the summary grid, every native client under its game, every browser and telnet program once, and the finder's script: about 3.5 minutes at 2400 bit/s, 35 seconds at 14,400), Browsers 20 KB, Telnet programs 18 KB, protocols 16 KB, the docs index 16 KB, the Eclipse page 11 KB, the ParlorNet rulebook page 9 KB, the game rulebooks page 22 KB, Run a server 22 KB, a client's page 12 KB, its ratings included (its screenshots, each a GIF of at most 320 pixels across and 21 KB, come on top), a doc one and a half times its Markdown plus 2 KB.
- Every address the game server's site has published still answers, with the page or a redirect; every link within the docs site resolves, to a file and, where it has one, an anchor on it.
- Downloads link to the author's page or to a public archive. The only files the docs site carries are its own: the patchers, the rulebooks' installer and the images, the diagrams among them.
- The client tables are lean: one row per client, in the browser's own text face (no FONT per cell, as in the docs), short OS text.
